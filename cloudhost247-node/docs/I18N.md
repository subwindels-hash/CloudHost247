# Localisation (i18n) — the language gate

The web application can be shown in more than one language, but a language is offered to visitors
**only when a complete, reviewed message catalogue exists for it**. This document states that
contract, where it is enforced, and exactly what adding a language involves.

Status: **English is the only offered language today.** No translated catalogue exists in the
repository, so no other language is listed. This is deliberate — see "Why the gate exists".

## Where the pieces live

| File | Role |
|---|---|
| `frontend/src/i18n/messages/en.ts` | English catalogue. The source of truth: every other catalogue must define every key it defines. |
| `frontend/src/i18n/locales.ts` | `LOCALES` — the languages the site offers. `findLocale`/`resolveLocale` resolve tags against it, `dir` carries text direction. |
| `frontend/src/i18n/LocaleProvider.tsx` | `CATALOGUES` — the loaded catalogues by locale code — plus the React context, `setLocale`, and the `<html lang>`/`<html dir>` side effect. |
| `frontend/src/i18n/catalogue.ts` | `createTranslator` (lookup order: locale, then English), `interpolate`, `pluralCategories`, `compareWithEnglish`. |
| `frontend/src/i18n/format.ts` | Locale-aware `formatCurrency`, `formatNumber`, `formatDate` (Intl-backed, safe on malformed tags). |
| `frontend/tests/unit/i18n-*.test.ts`, `language-switcher.test.tsx` | The gate itself. |

## The contract (enforced by tests, not by convention)

1. **One catalogue per listed locale, and no catalogue for an unlisted one.**
   `i18n-catalogues.test.ts` compares `Object.keys(CATALOGUES)` with `LOCALES`: they must be equal
   sets. Adding a language therefore cannot be "just a dropdown entry" — the catalogue must arrive
   with it, and adding a catalogue without listing it fails too.
2. **Completeness, per key.** Each catalogue must define every key in `en.ts` (`missing` empty) and
   nothing English does not define (`extra` empty).
3. **No empty or whitespace-only strings** in any catalogue.
4. **Placeholders survive translation.** `{count}`, `{name}`, `{year}`, `{legalName}` … must appear
   identically in every translation of a string.
5. **Plurals follow the target locale's own CLDR rules**, not English's two forms — see below.
6. **The switcher offers exactly what it can render.** `language-switcher.test.tsx` asserts the
   language count shown to the visitor and that an unlisted stored preference falls back to English.

## Plurals

Plural families are written `<base>.one`, `<base>.other`, e.g. `language.switcher.count.one` and
`language.switcher.count.other`. At runtime `t.plural('language.switcher.count', n)` selects the form
with `Intl.PluralRules` for the active locale, falling back to `.other`.

`compareWithEnglish(catalogue, locale)` is locale-aware:

* **required** — every category the locale can select (`Intl.PluralRules(locale)
  .resolvedOptions().pluralCategories`): `one`/`other` for English and German, `one`/`few`/`many`/
  `other` for Russian and Polish, `zero`/`one`/`two`/`few`/`many`/`other` for Arabic, `other` alone
  for Japanese and Chinese;
* **permitted** — only those categories. Carrying an English `one` form into a catalogue for a
  language that never selects it is reported as `extra`, not silently accepted;
* **unchanged** — every key that is not part of a plural family is compared literally, exactly as
  before, and any key English does not define is still `extra`. English's own key set is not
  affected by this rule.

## Adding a language

1. **Translate.** Copy `messages/en.ts` to `messages/<code>.ts` and translate every value — no key
   added, none dropped. Keep every `{placeholder}` byte-identical. Add the plural forms the target
   locale selects (see the table above; `pluralCategories('<code>')` prints them).
2. **Review.** A qualified speaker reads the whole catalogue against the English source. The legal
   footer line, the currency note ("You are charged in USD…"), and anything describing billing must
   be signed off explicitly — a mistranslated billing statement is a customer-facing defect, not a
   wording preference. Record the sign-off in the pull request.
3. **List and load.** Add the entry to `LOCALES` (`code`, `englishName`, `nativeName`, `dir`) and the
   import to `CATALOGUES` in `LocaleProvider.tsx`.
4. **Test.** `npx vitest run frontend/tests` must pass. Then update the two visitor-count assertions
   in `language-switcher.test.tsx` — the language count and, if the newly listed code was the
   "unsupported" example, a different code.
5. **Check the layout** for the new language: long compound words (German, Finnish), RTL
   (`dir: 'rtl'`, e.g. Arabic), and non-Latin scripts. Locale-prefixed routes do not exist; the
   switcher keeps the visitor on the same path, which is the "equivalent page" in this structure.

Nothing else in the codebase needs to change: `dir` sets `<html dir>`, region tags such as `pt-BR`
resolve to the base language, `Intl` formatting already takes the locale code, and any key missing at
runtime falls back to English rather than rendering a blank.

## Why the gate exists

A locale listed without a catalogue offers the visitor a choice that renders English, or raw message
keys. The switcher's own note states the promise to visitors — *"More languages are added once their
translations have been checked."* `locales.ts` states the same rule for maintainers. Unlisted
languages are not "missing": they are not offered, and a stored or browser preference for one falls
back to English (`resolveLocale`), so a visitor never lands in a half-translated site.

## Not verified here

Machine-checkable completeness is not translation quality. Native review, RTL layout behaviour,
script-specific font rendering, and translated-page rendering in a real browser remain
**staging-required** and are not claimed by the tests above. The legacy WHMCS string overrides under
`lang/overrides/` are unrelated to this frontend catalogue and are not used by the Node platform.
