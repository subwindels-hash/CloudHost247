# Visitor IP and privacy indicator

The React header requests `/api/v1/visitor/ip` on load, every five minutes while visible, and on reconnect or return to a visible tab. The address stays in component state; it is neither stored nor sent to analytics or a third party by this feature. The endpoint has `Cache-Control: private, no-store`, does not query a database, and does not log its response or address. Application request IP and common forwarding-header fields are redacted by the logger. Infrastructure access logs, reverse proxies, CDN logs, browser extensions and unrelated analytics are outside this feature's control and must be reviewed separately. The endpoint deliberately reports privacy status `unknown`: seeing an IP cannot prove whether VPN, proxy, or anonymity protection is used. No percentage or guarantee is shown.

## Deployment configuration (required)

The endpoint defaults to `VISITOR_IP_MODE=off` and returns `ip: null`. This is intentional: the Node app is normally behind cPanel/Apache, and blindly using the socket or trusting an arbitrary forwarding header could reveal the server/proxy address or allow spoofing. The UI then displays `IP: unavailable`. To enable real detection, an operator must verify the production topology and choose **one** of these modes:

* `VISITOR_IP_MODE=direct`: only when the Node process is directly connected to visitors, with no reverse proxy, CDN, load balancer or NAT gateway in front. The public socket address is used; forwarded headers are ignored.
* `VISITOR_IP_MODE=trusted-proxy`: set `VISITOR_IP_TRUSTED_PROXIES` to a comma-separated list of specific trusted peer IPs and/or CIDR ranges. This must include every legitimate proxy hop from the app back to the edge. Example syntax: `127.0.0.1,::1,10.20.0.0/24` (examples are not recommended production networks). At the network edge, ensure the proxy overwrites untrusted inbound `X-Forwarded-For`, or appends the observed client address correctly, and that no untrusted host can connect through an allowlisted peer. The resolver walks the X-Forwarded-For chain from right to left, stopping at the first untrusted public address. Missing, malformed, overly long or entirely trusted chains are rejected; invalid allowlists fail closed. Do not trust broad networks or the whole internet. Verify IPv4, IPv6 and spoofed headers from outside the proxy before enabling. Cloudflare's `CF-Connecting-IP` is not used by this implementation; the trusted edge must supply a properly sanitized X-Forwarded-For chain.

This configuration is independent of Fastify's global `trustProxy` setting and must not be inferred from it. Private, reserved and non-global IPs are not presented as a visitor's public IP. The feature does not determine a visitor's country or use an IP-reputation/VPN detection service. A validated provider and appropriate privacy disclosure would be needed before showing any positive or negative protection determination. This feature currently covers the React/Node site; the separate WHMCS/Smarty templates do not use this endpoint.
