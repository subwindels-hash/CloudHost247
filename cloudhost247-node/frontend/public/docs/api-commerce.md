# Commerce API Contract (Phase 5A)

This document is the API contract for Phase 5A, "Commerce foundation": a customer's cart and the
orders it becomes when checked out. Keep this in sync with the code — the source of truth is
`cloudhost247-node/src/routes/commerce.ts`, `cloudhost247-node/src/services/commerce-service.ts`,
and `cloudhost247-node/database/migrations/0014`–`0017`; this document should never describe
behavior the code doesn't actually have.

## Explicit non-goals (this phase)

- **No payment gateway, no payment record, no invoice, no billing ledger yet.** Every order this
  phase creates has `status: 'pending'` and `payment_status: 'unpaid'` and nothing in the codebase
  can currently change that — there is no route, job, or webhook that marks an order paid. Those
  land in Phase 5B (billing/invoices/ledger) and 5C/5D (payment gateway + webhooks).
- **No tax or discount configuration system yet.** `discount_amount` and `tax_amount` are always
  `"0.00"` on every order — a genuine zero, not a hidden or placeholder value. A future phase must
  add real tax/discount configuration before these become non-zero for any order.
- **No admin/staff order-viewing routes yet.** Deferred to Phase 5F. Nothing in this phase lets
  staff see, search, or act on another customer's cart or order.
- **No multi-currency support.** Every price, cart, and order in this phase is in a single
  platform-wide currency (see `src/config/billing.ts`'s `DEFAULT_CURRENCY`, currently `USD`). No
  request body field can ever change what currency is used.
- Nothing in this layer talks to cPanel/WHM, a domain registrar, or a payment provider. Placing an
  order records a purchase intent — it does not provision, activate, or configure anything.

## Architecture

```
Commerce API (Fastify routes)
  src/routes/commerce.ts        (/api/v1/cart/*, /api/v1/orders/*)
        │
        ▼
Service layer (the only place allowed to price anything)
  src/services/commerce-service.ts
        │            │
        ▼            ▼
Repository layer   Shared primitives
  src/db/carts.ts     src/db/transaction.ts  (withTransaction — real atomic multi-statement writes)
  src/db/orders.ts    src/lib/money.ts       (toCents/fromCents/multiplyCents/sumCents — integer-cent math)
        │
        ▼
PostgreSQL (database/migrations/0014..0017), joined through the existing Phase 3 catalog
  (products / product_plans / plan_pricing — database/migrations/0004..0006)
```

Every response is built only through `src/dto/commerce.ts` — the same "never leak an internal
field, never fabricate a price" mapping-layer pattern used by the Phase 3 catalog DTOs
(`src/dto/catalog.ts`) and Phase 4 account DTOs (`src/dto/account.ts`).

## Data model summary

- `carts` (`0014`) — exactly one cart per customer, enforced by a unique index on `user_id`.
  Created lazily (get-or-create) the first time a customer touches their cart; has no financial
  significance of its own.
- `cart_items` (`0015`) — a cart line references only `plan_id` (never a separate `product_id` —
  the product is always reached via `product_plans.product_id`, so it can never drift out of sync)
  plus a `billing_period`. No price is stored on a cart line; it is always resolved live from
  `plan_pricing` at read/checkout time. Unique on `(cart_id, plan_id, billing_period)` — adding the
  same plan+cadence again increases quantity instead of duplicating the line. `quantity` is capped
  at 20 per line (`cart_items_quantity_positive_check`).
- `orders` (`0016`) — the first genuinely financial table in the platform. `order_number` is
  generated by the database itself from a dedicated `order_number_seq` sequence
  (`'CH-' || lpad(nextval(...)::text, 8, '0')`) — atomic and race-free under concurrent checkouts,
  never client-supplied, never app-generated. `user_id` is `ON DELETE RESTRICT` (not `CASCADE`):
  a user with order history can never be deleted out from under it. `status` (`pending` /
  `completed` / `cancelled` / `failed`) and `payment_status` (`unpaid` / `pending` / `paid` /
  `failed` / `refunded` / `partially_refunded`) are separate columns — Phase 5A only ever produces
  `pending` / `unpaid`.
- `order_items` (`0017`) — an immutable price **snapshot** per line: `product_name_snapshot`,
  `plan_name_snapshot`, `unit_price_amount`, `currency`, and `line_total_amount` are copied at
  checkout time and never recalculated or updated afterward. `product_id`/`plan_id` are optional,
  best-effort soft links back to the live catalog (`ON DELETE SET NULL`) — a later catalog rename,
  price change, or deletion can never alter what a historical order says the customer agreed to
  pay. Every order display reads the `*_snapshot` columns, never the live catalog.

## Money handling

Every monetary DB column is Postgres `numeric`, which `pg`/`pglite` both return as a **string**
(e.g. `"19.99"`) specifically to avoid binary floating-point rounding. `src/lib/money.ts` is the
one place that converts a monetary string to a number, and always as a whole integer number of
cents — `toCents`/`fromCents`/`multiplyCents`/`sumCents`. No monetary arithmetic anywhere in the
commerce layer uses native JS `+`/`-`/`*` on a decimal string or float directly.

## Transactional integrity

`src/db/transaction.ts` exports `withTransaction(pool, fn)`, used by `checkoutCart` to make the
price re-check, the `orders`/`order_items` insert, and clearing the cart happen atomically — either
all of it commits, or (on any thrown error, including "cart is empty" or "item no longer
available") none of it does, and the customer's cart is left untouched. This closes a
check-then-act gap between reading a price and writing the order: two requests, or a catalog change
racing a checkout, can never produce a half-written order or an order priced from stale data.

In production, `withTransaction` checks out one dedicated `pg.Pool` client via `.connect()` and
runs `BEGIN`/the callback/`COMMIT`-or-`ROLLBACK` on that same client — calling `pool.query('BEGIN')`
followed by further `pool.query()` calls would **not** be a real transaction, because
`pg.Pool.query()` may use a different underlying connection per call. In tests, it uses
`@electric-sql/pglite`'s native `.transaction()` API instead.

## Authorization model

Every route calls `authenticate()` (re-verified against the database on every request, same as
Phase 4) and scopes every query to the caller's own `user_id`. A cart item or order that exists but
belongs to a different customer is never distinguishable from one that doesn't exist at all — both
return `404`, never `403`.

| Capability | customer | admin | super_admin |
|---|---|---|---|
| View/modify own cart | ✅ (self only) | ✅ (self only) | ✅ (self only) |
| Check out own cart into an order | ✅ (self only) | ✅ (self only) | ✅ (self only) |
| View own order history/detail | ✅ (self only) | ✅ (self only) | ✅ (self only) |
| View/modify another customer's cart or orders | ❌ | ❌ (deferred to 5F) | ❌ (deferred to 5F) |

## Price integrity rules (enforced in `src/services/commerce-service.ts`)

- **No request body ever carries a price, subtotal, tax, discount, total, or currency.** The only
  thing a client can specify is *what* it wants: `planId` + `billingPeriod` + `quantity`. Any such
  field present in a request body is silently ignored (zod schemas for these routes don't even
  define them), never validated against or trusted.
- Adding an item to the cart requires, at that moment: the plan `status = 'active'`, its parent
  product `status = 'active'` AND `visibility = 'public'`, and a `plan_pricing` row for that exact
  `(plan_id, billing_period, DEFAULT_CURRENCY)` with `effective_status = 'published'`. Any failure
  is a `404` (plan/product not purchasable) or `400` (no published price for that cadence) —
  the same "don't add a line that could never check out" rule applies to `checkoutCart`, which
  re-validates all of this fresh (not from cached cart-add-time data) inside the transaction.
- `GET /api/v1/cart` never hides a broken line — `priceUnavailable: true` and
  `hasUnavailableItems: true` surface honestly so the customer can remove/resolve it; an
  unavailable line is excluded from `subtotalAmount` (there is no valid price to add).
- `POST /api/v1/orders` refuses outright (with a `400` listing the affected plan names) if the cart
  is empty or any line is unavailable — no partial order is ever created.

## Endpoints

All endpoints require `Authorization: Bearer <token>` and return `401` if missing/invalid.

### `GET /api/v1/cart`

Returns the caller's own cart, creating it on first use.

```json
{
  "cart": {
    "items": [
      {
        "id": "…", "planId": "…", "productId": "…",
        "productName": "cPanel Hosting", "productSlug": "cpanel-hosting",
        "planName": "Starter", "planSlug": "starter",
        "billingPeriod": "monthly", "quantity": 2,
        "unitPriceAmount": "19.99", "lineTotalAmount": "39.98",
        "priceUnavailable": false
      }
    ],
    "currency": "USD",
    "subtotalAmount": "39.98",
    "itemCount": 2,
    "hasUnavailableItems": false
  }
}
```

### `POST /api/v1/cart/items`

Body: `{ "planId": "<uuid>", "billingPeriod": "one_time"|"monthly"|"quarterly"|"semi_annually"|"annually", "quantity"?: 1-20 (default 1) }`.
Upserts — adding a plan/cadence already in the cart increases its quantity. Returns `201` with the
updated cart summary (same shape as `GET /api/v1/cart`). `404` if the plan doesn't exist or isn't
currently purchasable; `400` if no published price exists for the requested cadence, or the body
fails validation.

### `PATCH /api/v1/cart/items/:id`

Body: `{ "quantity": 1-20 }`. Ownership-checked (`404` if the item doesn't exist or isn't the
caller's). Returns the updated cart summary.

### `DELETE /api/v1/cart/items/:id`

Ownership-checked removal. Returns the updated cart summary.

### `POST /api/v1/orders`

Checks out the caller's current cart. No request body is accepted or needed — currency is always
the platform default, prices are always re-read fresh inside one transaction. Returns `201` with
the created order (including its snapshot line items); `400` if the cart is empty or any line is no
longer available (nothing is created in that case).

```json
{
  "order": {
    "id": "…", "orderNumber": "CH-00000001",
    "status": "pending", "paymentStatus": "unpaid",
    "currency": "USD",
    "subtotalAmount": "39.98", "discountAmount": "0.00", "taxAmount": "0.00", "totalAmount": "39.98",
    "createdAt": "2026-…",
    "items": [
      { "id": "…", "productName": "cPanel Hosting", "planName": "Starter", "billingPeriod": "monthly",
        "quantity": 2, "unitPriceAmount": "19.99", "lineTotalAmount": "39.98", "currency": "USD" }
    ]
  }
}
```

### `GET /api/v1/orders`

Lists the caller's own orders (summaries, no line items), newest first.

### `GET /api/v1/orders/:id`

Full order detail including line items. Ownership-checked (`404`, not `403`, for another
customer's order — same as every other ownership check in this codebase).

## What's next (later Phase 5 sub-phases)

- **5B** — real invoices, a billing ledger (charges/payments/refunds/credits), and payment
  records, built on top of these `orders`.
- **5C** — a payment gateway abstraction (manual/offline + a self-contained sandbox gateway with
  simulated signed webhooks), checkout initiation.
- **5D** — signature-verified, idempotent, replay-protected webhooks that are the *only* way an
  order's `payment_status` can ever become `paid`.
- **5E/5F** — customer-facing billing UI and admin/staff billing management + audit trail.
- **5G** — SMTP notifications (order confirmation, invoice, payment) and reconciliation jobs.
