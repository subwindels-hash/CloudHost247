## 1. Defects found and fixed

Every item below was reproduced, fixed, and then given a gate so the same class of defect fails the
build rather than surviving a review.

### 1.1 The product catalogue rendered unstyled

`templates/cloudhost247/cloudhost247-product-catalog.tpl` (page `cloudhost247-hosting.php`) rendered
`ch247-catalog`, `ch247-product-grid` and `ch247-product-card__kind`. Those classes were defined
**only** in `templates/cloudhost247/css/custom.css`, and the theme's own stack
(`includes/site-head.tpl`) loads `site.css` then `design-system.css` — so the catalogue had no grid
at all and the plans stacked as plain articles, with a Bootstrap `btn btn-primary` for the call to
action.

The template now renders the design system's own plan components (`ch-plan-grid`, `ch-plan`,
`ch-table`, `ch-btn`), which are the components `includes/product-plans.tpl` and the application's
plan lists already use. `tests/ovh/test_public_catalog_static.py` used to assert `auto-fit` and
`@media(max-width:520px)` inside `css/custom.css` — asserting responsiveness of a stylesheet the
page never loaded. It now asserts the shipped sheet and every class the template renders.

### 1.2 The Builder page rendered unstyled chrome

The same file family: `cloudhost247-builder-page.tpl` used `ch247-preview-banner`,
`ch247-form-result`, `ch247-btn--primary` and `ch247-page`. The preview banner, the form result and
the sign-in button all rendered unstyled, so a draft preview looked like a finished page. The
template now uses `ch-note`, `ch-btn` and `ch-wrap--prose`, and keeps `ch247-root` — which is
required, because the Builder's own `runtime.css` scopes its typography to `.ch247-root`.

### 1.3 The global header had two unlabelled fields and one dead class

`includes/site-nav.tpl` labelled its search inputs with `class="ch-sr"`. `.ch-sr` is defined in
`tools.css`, which the *public* shell does not load, so both labels were invisible to a screen
reader. The labels now use `ch-visually-hidden`, which the design system defines. The same file
carried a `ch-mega-tools` modifier that no stylesheet or script ever defined (the Tools panel is
keyed by `data-ch-tools-menu`); it is gone.

### 1.4 The link audit skipped every template link

`scripts/site/check-links.mjs` skipped any href containing `{` or `$`, which is the dominant form in
this theme: `href="{$WEB_ROOT}/contact.php"`. The audit therefore never resolved those links. It now
substitutes the document root and checks the literal path that follows: **899** PHP links are
checked, up from 824, and no broken destination was found once the check was turned on. Static
assets with a file extension are also resolved against the repository instead of being accepted as
unknown-but-plausible routes.

### 1.5 One published page kept its own accent colour

`css/email-hosting.css` declared `--ch247-email-accent: #1c64f2` — a private blue palette with no
counterpart anywhere else in the theme, so the Email Hosting page was the one public page whose
accents disagreed with the rest of the site. All seven of its colour variables and six literal
hexes now point at shared design tokens.

### 1.6 The AVIF half of the image ladder was missing where the platform serves it

`visual.tpl` and `Illustration.tsx` advertise `-640/-960/-1280` in AVIF and WebP. A `<source>` whose
URL 404s does not fall through to the next source, so a missing encoding is a blank illustration.

The ladder was complete in the theme library and in `cloudhost247-node/public/media/cloudhost247` —
but that directory is the **build output**, and `frontend/vite.config.ts` sets
`outDir: ../public` with `emptyOutDir: true`: the next `vite build` replaces it with a copy of the
Vite public directory, which did not have a single AVIF file. `scripts/generate-raster-formats.py
--emit-served` was targeting the build output; it now targets
`cloudhost247-node/frontend/public/media/cloudhost247` (tracked, 333 files) and the mirror test
requires it and compares bytes rather than names. The old test checked the git-ignored build
directory and skipped silently on a clean checkout.

### 1.7 The raster check required the encoder, so the release gate failed on CI

`--check` is the last step of the release gate, and it called `require_imagemagick()` before doing
anything — so on the GitHub runner, which installs neither `convert` nor `identify`, the gate ended
with `ImageMagick \`convert\` is not on PATH` and the release candidate went red for a ladder that was
complete. Verification must not need the encoder: the source width is a field in the JPEG, so
`--check` now parses the start-of-frame header itself and the converter is required only on the
writing path. Checked with `convert` and `identify` hidden (check passes, writing still refuses
loudly), and with a variant deleted (check still fails). The parsed widths match `identify` on all 20
sources.

This one was found by watching the pull request's checks, not by running the gate locally: the local
machine is not the release environment, and it has ImageMagick.

## 4. Deliberate decisions

* **`css/custom.css` stays.** It is not part of the public stack, but the platform loads
  `templates/<theme>/css/custom.css` by convention on every client-theme page, and the rules that
  keep WHMCS-owned surfaces (client area, tables, forms, modals, Bootstrap mobile stacking) and its
  focus/mobile/reduced-motion floor are asserted by `tests/security/test_security.py`. The file now
  says so at the top, and says not to add page styles to it.
* **Five navigation entries have no SPA route** (`Knowledge Base`, `Announcements`, `Plesk Hosting`,
  `Domain DNS`). They are PHP-surface destinations: the WHMCS knowledge base and announcements do not
  exist in the application, and neither does a Plesk page. The generator drops them from the SPA
  projections and the theme always links the PHP route, so neither surface can render a dead link.
  The tools-family entries are resolved to their SPA routes because `/tools/*` is an application
  route.
* **Cross-column label variants stay** (`Web Hosting` in the Hosting menu, `Web hosting` elsewhere).
  They are the same page named for the column it sits in; the enforced rule is one destination per
  link, and one destination per column.
* **Sample and state routes stay, unlinked and disallowed.** `cloudhost247-sample.php`,
  `all-element-cloudhost247.php`, `tables.php`, `future-element.php` and the two `-sample` pages are
  `Disallow`ed in `robots.txt` and linked from nowhere. `comingsoon.php` and `notfound.php` answer
  404 until the operator publishes wording for them, which is a product state rather than a
  placeholder. `dedeicated-server.php` is a 301 to the correctly spelled route; the navigation is
  forbidden from linking it.
