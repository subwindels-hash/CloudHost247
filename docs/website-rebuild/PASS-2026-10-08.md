# Public website — presentation pass, 2026-10-08

**Branch:** `arena/4c00ccfe-cloudhost247`
**Deployment state:** **not deployed.** Production release remains gated on WHMCS staging verification.
**Scope:** the public presentation layer (theme, design system, public PHP pages, SPA marketing
surfaces, navigation projection, image pipeline) and the source gates that hold it. No WHMCS core,
provisioning, billing, authentication, server-module, API, Builder or integration code was changed.

This pass continued the rebuild recorded in `CONTINUATION-REPORT.md`. It fixed defects that the
existing gates could not see, and it closed the gaps that let them through.

---

## 1. Defects found and fixed

Every item below was reproduced, fixed, and then given a gate so the same class of defect fails the
build rather than surviving a review.

### 1.1 The product catalogue rendered unstyled

`templates/cloudhost247/cloudhost247-product-catalog.tpl` (page `cloudhost247-hosting.php`) rendered
`ch247-catalog`, `ch247-product-grid` and `ch247-product-card__kind`. Those classes were defined
**only** in `templates/cloudhost247/css/custom.css`, and the theme's own stack
(`includes/site-head.tpl`) loads `site.css` then `design-system.css` — so the catalogue had no grid
at all and the plans stacked as plain articles, with a Bootstrap `btn btn-primary` for the call to
action.

The template now renders the design system's own plan components (`ch-plan-grid`, `ch-plan`,
`ch-table`, `ch-btn`), which are the components `includes/product-plans.tpl` and the application's
plan lists already use. `tests/ovh/test_public_catalog_static.py` used to assert `auto-fit` and
`@media(max-width:520px)` inside `css/custom.css` — asserting responsiveness of a stylesheet the
page never loaded. It now asserts the shipped sheet and every class the template renders.

### 1.2 The Builder page rendered unstyled chrome

The same file family: `cloudhost247-builder-page.tpl` used `ch247-preview-banner`,
`ch247-form-result`, `ch247-btn--primary` and `ch247-page`. The preview banner, the form result and
the sign-in button all rendered unstyled, so a draft preview looked like a finished page. The
template now uses `ch-note`, `ch-btn` and `ch-wrap--prose`, and keeps `ch247-root` — which is
required, because the Builder's own `runtime.css` scopes its typography to `.ch247-root`.

### 1.3 The global header had two unlabelled fields and one dead class

`includes/site-nav.tpl` labelled its search inputs with `class="ch-sr"`. `.ch-sr` is defined in
`tools.css`, which the *public* shell does not load, so both labels were invisible to a screen
reader. The labels now use `ch-visually-hidden`, which the design system defines. The same file
carried a `ch-mega-tools` modifier that no stylesheet or script ever defined (the Tools panel is
keyed by `data-ch-tools-menu`); it is gone.

### 1.4 The link audit skipped every template link

`scripts/site/check-links.mjs` skipped any href containing `{` or `$`, which is the dominant form in
this theme: `href="{$WEB_ROOT}/contact.php"`. The audit therefore never resolved those links. It now
substitutes the document root and checks the literal path that follows: **899** PHP links are
checked, up from 824, and no broken destination was found once the check was turned on. Static
assets with a file extension are also resolved against the repository instead of being accepted as
unknown-but-plausible routes.

### 1.5 One published page kept its own accent colour

`css/email-hosting.css` declared `--ch247-email-accent: #1c64f2` — a private blue palette with no
counterpart anywhere else in the theme, so the Email Hosting page was the one public page whose
accents disagreed with the rest of the site. All seven of its colour variables and six literal
hexes now point at shared design tokens.

### 1.6 The AVIF half of the image ladder was missing where the platform serves it

`visual.tpl` and `Illustration.tsx` advertise `-640/-960/-1280` in AVIF and WebP. A `<source>` whose
URL 404s does not fall through to the next source, so a missing encoding is a blank illustration.

The ladder was complete in the theme library and in `cloudhost247-node/public/media/cloudhost247` —
but that directory is the **build output**, and `frontend/vite.config.ts` sets
`outDir: ../public` with `emptyOutDir: true`: the next `vite build` replaces it with a copy of the
Vite public directory, which did not have a single AVIF file. `scripts/generate-raster-formats.py
--emit-served` was targeting the build output; it now targets
`cloudhost247-node/frontend/public/media/cloudhost247` (tracked, 333 files) and the mirror test
requires it and compares bytes rather than names. The old test checked the git-ignored build
directory and skipped silently on a clean checkout.

### 1.7 The raster check required the encoder, so the release gate failed on CI

`--check` is the last step of the release gate, and it called `require_imagemagick()` before doing
anything — so on the GitHub runner, which installs neither `convert` nor `identify`, the gate ended
with `ImageMagick \`convert\` is not on PATH` and the release candidate went red for a ladder that was
complete. Verification must not need the encoder: the source width is a field in the JPEG, so
`--check` now parses the start-of-frame header itself and the converter is required only on the
writing path. Checked with `convert` and `identify` hidden (check passes, writing still refuses
loudly), and with a variant deleted (check still fails). The parsed widths match `identify` on all 20
sources.

This one was found by watching the pull request's checks, not by running the gate locally: the local
machine is not the release environment, and it has ImageMagick.

### 1.8 The Builder's widget markup had no class audit, and 46 classes were unstyled

The theme class audit reads Smarty templates. The Builder renders its own markup in PHP
(`WidgetRenderer`), so nothing looked at it — and the cart, the four brokerage widgets and their rows,
the form title, the image element and the status label all emitted `ch247-*` class names that no
stylesheet defines (`runtime.css` has 129 of the 149, none of the rest). A published Builder page
therefore rendered those widgets as plain stacked text inside an otherwise finished page.

`scripts/audit-builder-widget-classes.py` now extracts every class the renderer can emit — including
names composed from a literal prefix plus a variable — and requires each to have a rule in the sheet
the Builder serves. Two things keep it honest:

* the 20 classes that carry no rule **on purpose** are an explicit, named table with a reason each
  (heading elements are styled by `.ch247-root h1..h6`, `ch247-star` is sized by its svg attributes,
  the rest are plain wrappers whose children carry the layout), and an exemption that no longer
  matches anything the renderer emits fails the audit;
* a plain class must match **exactly**. The first version accepted a suffix, so renaming
  `.ch247-broker-pricing__amount` to `...__amount-renamed` — which loses the rule — still passed.
  Mutation testing caught that, and the matcher was fixed.

The missing styles were then written into `runtime.css` using the file's existing tokens and
patterns: the cart and brokerage panels join the card treatment, the fee rows become spaced
`justify-content: space-between` rows, the case rows wrap with the domain taking the slack, the
brokerage input matches `.ch247-input`, and `.ch247-status__label` takes `flex: 1` so the state and
timestamp line up. `#fff` and the star gold now come from tokens (`--ch247-color-surface`,
`--ch247-color-warning`); the three remaining literals are the soft result/unavailable palettes,
which the Builder's token set has no family for, and they are named in the test.

Four mutations prove the gate: a renamed selector, a newly emitted unstyled class, a stale
exemption, and a substring-only near-miss each fail it by name, and the tree is clean again after.

### 1.9 The Domain menu's DNS column linked a page only one of the two surfaces serves

`§1.2` fixed the menus; this is the same column read line by line against both catalogues. Two
defects, and the second is the reason the first survived the gates.

**`DNS Health` pointed at `/tools/dns-health`, which the tools shell cannot serve.** The registry
publishes one destination and two surfaces answer it: the React app resolves
`cloudhost247-node/src/tools/catalog.ts`, the PHP tools front controller resolves `config/tools.php`.
The capability exists in both — the app slugs it `dns-health`, the native catalogue `domain-dns-health`
— so the menu worked in the SPA and 404'd in the tools shell. `whois` → `domain-whois` is the same
shape already handled in that file, so `dns-health` now publishes `/tools/domain-dns-health` for both
surfaces and keeps `/tools/dns-health` as a forwarding alias. The only other link to the alias was in
`DomainHealthPage.tsx`, which now points at the published path.

**The gate that should have caught it was reading the wrong catalogue.** `phpTargetExists()` in
`scripts/site/generate.mjs` builds its route set from `tools.json` — the projection of the *app*
catalogue — and calls it "the routes the PHP Tools surface actually resolves". The PHP surface
resolves `tools-public.json` (`config/tools.php`), so the nav's PHP destinations were validated
against the app's paths: exactly the mismatch the check exists to prevent. It now takes tool paths
from the native export and only categories and collections from the app projection; with the dead
link restored the generator fails with
`menu:domains/DNS: "DNS Health" → tools/dns-health does not exist and is not a WHMCS entry point.`

**`DNS Security` promised tools the Security category does not contain.** It pointed at
`/tools/category/security` described as "DNS and domain security tools", and the category holds
`api-key-generator`, `checksum-hash-generator`, `http-security-headers-generator` and
`password-policy-generator` — no DNS tool at all. The item now closes the column honestly as
`All DNS Tools` → `/tools/category/dns-domains`, the category that does hold the DNS family.

Two gates, each mutation-tested:

* `tests/tools/site-integration.php` walks every tools destination the published navigation carries
  (`Site::catalog()`) and requires the **native** catalogue to resolve it — strictly, without the
  theme runtime's app-aware fallback, because this deployment is the tools tree on its own. It also
  pins `tools-public.json` to `config/tools.php` (same tool paths), so the export the generator reads
  cannot go stale and answer for a shell it no longer describes;
* `scripts/site/generate.mjs` now fails the build on a nav destination the native catalogue cannot
  serve, before anything is written.

Restoring the dead link fails the generator; drifting the export fails the PHP suite with
`/tools/dns-checker, /tools/dns-health`. Both are clean again afterwards.

### 1.10 Nothing said which absent templates were the parent's, and which were a hole

`templates/cloudhost247` is a child of `twenty-one` (`theme.yaml`). It ships the 62 templates it
restyles and inherits the platform's own partials — `includes/head.tpl`,
`includes/navbar.tpl`, `includes/sidebar.tpl`, `includes/breadcrumb.tpl`, the two email
modals and the network-status notice — which are absent from this repository **by design**, because
they belong to the vendor theme in a WHMCS installation.

That design was nowhere stated. A reader (and a gate) saw eight `{include file="$template/…"}`
statements pointing at files that do not exist, indistinguishable from a partial someone deleted in
the rebuild. The `orderforms/ovh_cart` child theme has the same shape against its `standard_cart`
parent, and there it reaches the parent by naming its directory outright
(`orderforms/standard_cart/common.tpl`).

So the absences are now declared rather than assumed: `PARENT_TEMPLATES` in
`scripts/verify-website.py` lists each parent-served template with the parent it comes from, and
`include_errors()` fails on

* an include the theme neither ships nor covers with such a declaration — the removed partial or the
  typo, which renders a hole in the page;
* a first-party include (`cloudhost247/includes/…`) that no longer exists on disk;
* a theme that declares no `parent:` but still relies on one;
* an exemption gone **stale** — the theme now ships the template itself, or nothing includes it any
  more. A stale exemption is the way a gate quietly stops covering what it was written for, so it is
  a failure, not a note.

Dynamic includes are skipped, not guessed: `{include file=$legalTemplate}` is decided by data at
render time, and a value still assembled from Smarty (`orderforms/{$carttpl}/common.tpl`) is not a
path yet. The vendor-era `*_legacy` order-form tree is out of scope for the same reason
`check-links.mjs` reports rather than fixes it. 79 includes are audited across the rebuilt themes.

Mutation-proofed on the real tree: adding `$template/includes/removed-partial.tpl` to `header.tpl`
fails with `includes $template/includes/removed-partial.tpl, which the theme does not ship and no
parent declaration covers`; copying a file to `includes/head.tpl` fails with `the exemption for
includes/head.tpl is stale - the theme now ships it`; removing the breadcrumb include fails with
`the exemption for includes/breadcrumb.tpl is stale - nothing includes it any more`. All three pass
again once reverted.

## 4. Deliberate decisions

* **`css/custom.css` stays.** It is not part of the public stack, but the platform loads
  `templates/<theme>/css/custom.css` by convention on every client-theme page, and the rules that
  keep WHMCS-owned surfaces (client area, tables, forms, modals, Bootstrap mobile stacking) and its
  focus/mobile/reduced-motion floor are asserted by `tests/security/test_security.py`. The file now
  says so at the top, and says not to add page styles to it.
* **Five navigation entries have no SPA route** (`Knowledge Base`, `Announcements`, `Plesk Hosting`,
  `Domain DNS`). They are PHP-surface destinations: the WHMCS knowledge base and announcements do not
  exist in the application, and neither does a Plesk page. The generator drops them from the SPA
  projections and the theme always links the PHP route, so neither surface can render a dead link.
  The tools-family entries are resolved to their SPA routes because `/tools/*` is an application
  route.
* **Cross-column label variants stay** (`Web Hosting` in the Hosting menu, `Web hosting` elsewhere).
  They are the same page named for the column it sits in; the enforced rule is one destination per
  link, and one destination per column.
* **Sample and state routes stay, unlinked and disallowed.** `cloudhost247-sample.php`,
  `all-element-cloudhost247.php`, `tables.php`, `future-element.php` and the two `-sample` pages are
  `Disallow`ed in `robots.txt` and linked from nowhere. `comingsoon.php` and `notfound.php` answer
  404 until the operator publishes wording for them, which is a product state rather than a
  placeholder. `dedeicated-server.php` is a 301 to the correctly spelled route; the navigation is
  forbidden from linking it.
