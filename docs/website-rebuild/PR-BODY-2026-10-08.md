# Public website: seven-family navigation, one served stylesheet stack, and gates for what the old ones could not see

Branch `arena/4c00ccfe-cloudhost247` · Base `main` · **not deployed** — production release stays gated on WHMCS staging verification.

Report: `docs/website-rebuild/PASS-2026-10-08.md` · Archive: `CloudHost247-production-2.1.0.zip` (8,601 members, 99.0 MB, extracted and re-tested)

The presentation layer of the public site — theme, design system, public PHP pages, SPA marketing
surfaces, navigation projection and the image pipeline — plus the source gates that hold it. No WHMCS
core, provisioning, billing, authentication, server-module, API, Builder or integration code changed.

## What this PR changes

**The header publishes the seven families the brief names.** The nine-menu structure becomes Hosting,
Cloud & Servers, Domains, Platforms, Tools, Resources and Company, with an eight-column footer.
Developers and Websites fold into Platforms and Hosting, so no destination is reachable from two
top-level panels. The registry gained the rules the brief asks for but nothing enforced: duplicate
label+destination inside one menu, one destination twice in a footer column, `href="#"`, empty,
`javascript:` and scheme-relative destinations, trailing slashes, non-lower-case router paths, PHP
filename casing and obsolete routes.

**Navigation tests that were tautologies now pin facts.** The served menu was compared against the
generated module it is served *from*, so deleting a destination moved both sides and the test stayed
green; it now pins the destinations each family must publish and the advertised `linkCount` against
the structure actually served — the mutation that used to pass now fails with
`cloud must publish /cloud/backups`. The header test's bare menu count is replaced with the published
ids and footer titles.

**Vendor artwork left the catalogue, and cannot come back.** `frontend/public/panel-logos` and
`os-logos` held real vendor artwork — the Ubuntu roundel, the cPanel wordmark in `#FF6C2C`, Debian in
`#A80030`, openSUSE in `#73BA25` — on a catalogue whose rows are almost all DISABLED, implying an
endorsement no vendor gave. They are now the CloudHost247 marks, byte-identical to the canonical
files, and a sweep over every SVG the project serves fails if a vendor brand colour returns.
`templates/orderforms/ovh_cart/` is a named, documented exemption because it is a vendor skin in the
strict integrity baseline.

**Three pages rendered unstyled in a browser while their tests passed.** The product catalogue and the
Builder page rendered `ch247-*` classes that exist only in `css/custom.css` — a stylesheet the theme
does not load — and the global header labelled its search fields with `.ch-sr`, which only `tools.css`
defines. The catalogue now uses the design system's `ch-plan-grid`/`ch-plan` (the components
`product-plans.tpl` and the SPA plan lists already use), the Builder page uses `ch-note`/`ch-btn` and
keeps `ch247-root` because the Builder's own `runtime.css` scopes all its typography to it. The test
that "proved" the catalogue responsive asserted `auto-fit` inside the dead sheet; it now asserts the
shipped sheet and every class the template renders.

**One published page had its own accent colour.** `email-hosting.css` declared
`--ch247-email-accent: #1c64f2`, a private blue palette no other page used. All seven of its colour
variables and six literal hexes now alias shared design tokens.

**The link audit skipped the theme's dominant link form.** `check-links.mjs` skipped any href
containing a Smarty tag — that is `{$WEB_ROOT}/page.php`, the commonest link in this theme. It now
substitutes the document root and checks the path: **899 PHP links, up from 824**, all resolving.

**The AVIF half of the image ladder was missing where the platform serves it.** `visual.tpl` and
`Illustration.tsx` advertise `-640/-960/-1280` in AVIF and WebP; a `<source>` whose URL 404s does not
fall through, so a missing encoding is a blank illustration. The ladder was complete in the theme
library and in the build output — but `vite.config.ts` sets `emptyOutDir: true` on `../public`, so the
next build replaces it with a copy of Vite's public directory, which had no AVIF at all.
`--emit-served` now targets that directory (tracked, 333 files) and the mirror test requires it and
compares bytes instead of names; the old test checked the git-ignored build output and skipped
silently on a clean checkout.

**Two defects that were hiding each other.** `managed-services.php` and `server-management.php`
published the same title-level metadata because the registry pointed the Hosting menu's "Managed
Services" item at `/cloud/server-management` while naming `managed-services.php` as its page. The
reason it went unnoticed: `emitPhpSiteJson` ran *after* the `errors.length` gate, so every `fail()`
inside the projection was unreachable. Managed Services has its own route and the projection's checks
now run.

**The tools engine's standalone shell linked pages it does not serve.** `tools/lib/View.php`
hardcoded `/web-hosting.php` and `/contact.php` — the website's own pages, absent in a tools-only
deployment — and built its brand link from the domain root, so a subpath mount pointed outside itself.

**An exported package no longer looks broken.** Seven suites assert how the *repository* is wired
(registered in `.github/workflows/independent-foundation.yml`, `*.zip` stays in `.gitignore`), and the
archive excludes both files on purpose. Those assertions now skip, visibly and with a reason, when the
metadata is absent. Inside the repository nothing skips.

**A mega-menu link that only one of the two surfaces served.** The registry publishes one
destination and two catalogues answer it: the React app resolves
`cloudhost247-node/src/tools/catalog.ts`, the PHP tools shell resolves `config/tools.php`. The Domain
menu's `DNS Health` item pointed at `/tools/dns-health` — the app's slug — so it worked in the SPA and
404'd in the tools shell. The generator's own PHP-side check missed it because it built its route set
from `tools.json`, the projection of the *app* catalogue; it now validates against the native export,
and `dns-health` publishes the path both surfaces serve (`/tools/domain-dns-health`) with the old one
kept as a forwarding alias. `tests/tools/site-integration.php` walks every tools destination the
navigation publishes and requires the native catalogue to resolve it, and pins the export to
`config/tools.php` so the file the generator reads cannot go stale. The same column's `DNS Security`
item promised DNS tooling while pointing at the Security category, which holds key, hash and policy
generators; it now closes the column as `All DNS Tools` → the DNS category.

**The Builder's widget markup is styled again — and audited.** The theme class audit reads Smarty
templates; the Builder renders its markup in PHP, so nothing looked at it. The cart, the four
brokerage widgets and their rows, the form title, the image element and the status label all emitted
`ch247-*` class names that no stylesheet defines — 46 of the 149 the renderer can emit — so those
widgets rendered as plain stacked text inside an otherwise finished page. The missing styles now use
the sheet's existing tokens and patterns, and `scripts/audit-builder-widget-classes.py` keeps it that
way: it extracts every class the renderer can emit (including names composed from a prefix plus a
variable), requires a rule for each, and carries a named, reasoned table for the 20 classes that are
hooks — an exemption that stops matching anything fails the audit. Mutation-tested four ways: a
renamed selector, a newly emitted unstyled class, a stale exemption and a substring-only near-miss
each fail it by name.

**The raster check no longer needs the encoder.** `--check` is the last step of the release gate and
it demanded ImageMagick before doing anything, so on the GitHub runner — which installs neither
`convert` nor `identify` — the gate ended with `ImageMagick \`convert\` is not on PATH` and the whole
release candidate went red for a ladder that was complete. Verification must not depend on the
encoder: the source width is a field in the JPEG, so it is now parsed from the start-of-frame header
and the converter is required only on the writing path. This one was found by watching the pull
request's checks rather than trusting the local run — the local machine is not the release
environment, and it has ImageMagick.

| `check-links.mjs` document-root links | an unresolvable `{$WEB_ROOT}/…` destination |
| `tests/tools/site-integration.php` shell contract | a shell link that does not resolve in a tools deployment (1,133 assertions, up from 1,000) |
| `tests/builder/test_static.py` | the Builder page losing its `.ch247-root` scope hook, or an interpolation losing `|escape` |
| `tests/website/test_static.py` mirror check | a missing or byte-different ladder file in Vite's public directory |
| `generate-raster-formats.py --check` | a scene missing any advertised encoding — pure Python, so it runs where the encoder is not installed |
| `scripts/audit-builder-widget-classes.py` | a widget class no served sheet defines, or a hook exemption that no longer matches anything the renderer emits |
| `scripts/site/generate.mjs` + the walk in `tests/tools/site-integration.php` | a menu destination the tools shell cannot resolve, or a `tools-public.json` that has drifted from `config/tools.php` |

| `tests/website/test_static.py` vendor-colour sweep | a vendor brand colour anywhere in the served SVG library |

Every gate was proven by mutation: the dead catalogue class, the header's `ch-sr`, a removed grid
definition, the restored blue accent, a deleted mirror file, the old hardcoded shell, the removed

owns them, and the repository is clean again afterwards.

## Deliberate decisions

* **`css/custom.css` stays.** It is not part of the public stack, but the platform loads
  `templates/<theme>/css/custom.css` by convention on every client-theme page, and the rules keeping
  WHMCS-owned surfaces and the focus/mobile/reduced-motion floor are asserted by the security suite.
  Its header now says what it is for and that page styles do not belong there.
* **Five navigation entries have no SPA route** (`Knowledge Base`, `Announcements`, `Plesk Hosting`,
  `Domain DNS`). They are PHP-surface destinations — WHMCS owns the knowledge base and announcements,
  and there is no Plesk page in the application. The generator drops them from the SPA projections and
  the theme always links the PHP route, so neither surface can render a dead link.
* **Cross-column label variants stay** (`Web Hosting` in the Hosting menu, `Web hosting` elsewhere).
  Same page, named for its column; the enforced rules are one destination per link and per column.
* **Sample and state routes stay, unlinked and disallowed.** `comingsoon.php` and `notfound.php`
  answer 404 until the operator publishes wording — a product state, not a placeholder.
* **The browser suites are still staging-gated.** Nothing here claims a rendered result that only a
  browser or a live WHMCS installation can produce.
