## 2. P0 and other no-proof findings

### F1 — public database status can be falsely operational (P0)

`src/routes/health.ts` calls `isDatabaseReachable` in `/ready` and checks the boolean, but `/api/v1/public/status` awaits it without checking the returned boolean and changes the local status only on an exception. A rejected query can be converted to `false` by the helper, so the database component can remain `operational`. The earlier audit reproduced `/ready` 503 alongside an operational public DB component; this slice inspected source only and did not repeat that outage. The public website component is also asserted operational based on serving the response; an independent public reachability probe is not established here.

### F2 — SSL records and UI do not prove CA operations (P0)

- `src/routes/ssl.ts`: with submitted PEM the create route sets `ISSUED` and an expiry 90 days from now without parsing/validating the certificate; without PEM it stores `PENDING`.
- The renew route sets `ISSUED` and moves expiry by 90 days with no CA call; the revoke route changes the local status to `REVOKED` without a CA revocation call. The delete route removes the local row; its response does not establish remote revocation.
- `frontend/src/pages/SslManagementPage.tsx` says automated ACME validation is in progress following a request and advertises automatic issuance and 90-day renewal. Those claims need to match verified operations. Read-path consumers include `src/ai-os/tools/implementations.ts` and `src/ai-os/jobs/sweep.ts`, which can repeat the stored status/expiry.
- The domain SSL intent route and deployment pipeline are separate. A pending request, delegated resolver configuration or a local record is not evidence of issuance, installation, renewal or revocation.

### F3 — base panel stubs and inferred monitoring (P0)

`src/control-panels/adapters/base.ts` supplies 18 inherited adapter instances through `src/control-panels/registry.ts`. The base methods `install` (payload generated), `uninstall`, `configure`, `getStatus`, `healthCheck`, `createAccount`, `suspendAccount`, `unsuspendAccount`, `terminateAccount`, `createDomain`, `deleteDomain`, `createSubdomain`, `createDatabase`, `deleteDatabase`, `createEmailAccount`, `deleteEmailAccount`, `createDNSRecord`, `deleteDNSRecord`, `issueSSL`, `renewSSL`, `getUsage`, and `restartService` return successful/active/healthy/online or completed-sounding results without an upstream operation in those methods. Some capability checks only gate whether a stub returns; they do not perform the operation. `install` specifically says a payload was generated, not that installation was completed, but its `success: true` must not be misread downstream.

Static source search found production registry uses at `src/control-panels/registry.ts` (installation script generation), `src/infrastructure/services/server-configurator.ts` (cloud-init path), `src/db/firewall.ts` (firewall port metadata), and an import in `src/routes/monitoring.ts`; tests also use registry helpers. **No direct production invocation of the base operational methods was found by the searches recorded below**; this does not rule out dynamic, external or deployment-specific callers. Do not claim the stub is currently customer-invocable without a traced path. Review all inherited overrides and dynamic references before closing this slice.

Independently, `src/routes/monitoring.ts` derives `panelHealth: HEALTHY` and SSH/HTTP/HTTPS `ONLINE` from `server.status === 'active'`, without probing those services there; its initial server health is `HEALTHY` for other statuses absent contrary metrics. Treat these as source-observed false-confidence risks, not evidence of a live outage. Verify freshness, upstream semantics and customer UI before remediation.

### F4 — simulation and payment boundaries require review

- `src/deployments/adapters/cpanel-adapter.ts`, `docker-adapter.ts` and `kubernetes-adapter.ts` contain explicit simulation branches; `src/config/env.ts` defaults `DEPLOYMENT_SIMULATION_MODE` to false but the inspected configuration schema allows a boolean. `src/worker/main.ts` passes it to the deployment engine, and `src/services/instance-operations.ts` passes it to direct reads. `src/deployments/engine.ts` marks backup rows `completed` when `runBackup` returns `ok`, including an explicit cPanel simulated-backup result. The deployment pipeline separately avoids marking an application healthy when health is unknown. Verify production mode restrictions and UI/status propagation rather than assuming simulation is safely excluded.
- `src/payments/gateway-registry.ts` lists **manual and internal sandbox** for initiation; Stripe/PayPal/Paystack are registered as webhook handlers, not as initiation gateways in that registry. `src/payments/stripe-gateway.ts` has an initiation method that returns a `pi_mock_...` reference, but this inspection found no registered production initiation path to it. `paystack-gateway.ts` similarly constructs a local reference. Do not describe these as working live payment initiation; trace other callers and configuration independently.
- `src/payments/sandbox-gateway.ts` explicitly says its payment is simulated. Its webhook can model success and `src/services/webhook-service.ts` consumes registered handlers. Trace whether configuration permits demo transactions or webhook-driven fulfillment to affect production state; that is **not yet proven** from this inspection. The sandbox is not a third-party provider sandbox.
- `src/infrastructure/providers/mock-adapter.ts` documents explicit development opt-in, production refusal and mock-labelled resources. These safeguards do not constitute a live VPS verification.
