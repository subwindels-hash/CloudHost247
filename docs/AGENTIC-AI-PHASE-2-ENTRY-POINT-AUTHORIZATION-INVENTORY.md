# Phase 2 — orchestration entry-point authorization inventory

**Local implementation review, not an independent security review or certification.** This document traces the nine declared server-side entry points to their callers and identifies boundaries that remain open. It does not establish production configuration, deployment, security sign-off, or ongoing authorization after dispatch.

| Entry point | Caller and initial authority | Additional admission/fencing | Important remaining limitation |
| --- | --- | --- | --- |
| `admin.task` | `controllers/routes.ts` POST `/admin/ai/tasks`: `ai.tasks.run`, with DB-rechecked role/status via `requireAiPermission`; actor comes from authentication. | Agent lookup and declared task type, central entry-point/scope contract, grant admission, executor scope and agent/tool checks. | Original actor role/status and ai.tasks.run are rechecked under a row lock at claim; there is no fence after claim or around effects, and an admin may supply customer/subject fields. |
| `admin.copilot` | POST `/admin/ai/copilot`: `ai.copilot.execute`; fixed copilot agent/task and authenticated actor. | Contract denies customer scope; executor and tool gates. | Original actor role/status and ai.copilot.execute are rechecked under a row lock at claim; later revocation cannot recall execution. |
| `admin.board.briefing` | POST `/admin/ai/board/briefings`: `ai.board.briefings`; authenticated actor supplied to board service. | Server selects CEO and task, contract denies customer scope, duplicate task is not restarted. | Original actor role/status and ai.board.briefings are rechecked under a row lock at claim; later revocation cannot recall execution, and report reuse and publication need operational review. |
| `schedule.scan` | `worker/main.ts` runs `runAiSweep`; the sweep uses server-defined agent/task/input and bucket keys, not an HTTP actor. | Registry grant, bucket/idempotency checks; existing queued task is not restarted. | Trust rests on worker execution/deployment and database access, not a per-task human permission. Bucket bookkeeping is not an effect fence. |
| `schedule.board.briefing` | `runAiSweep` calls `generateExecutiveBriefing` with a null actor and fixed daily type. | Scheduled contract, period key and duplicate-task refusal. | Trust rests on the worker; period idempotency does not certify downstream effects. |
| `workflow.event` | Sweep or permission-gated admin event route calls `processPendingEvents`; engine claims a persisted event and loads enabled workflows. Admin emission and workflow changes require `ai.workflows.manage`. | Non-expiring event claim, validated workflow snapshot, agent preflight, transactional task preparation and checkpoint; failed/uncertain work holds the claim. | The claim establishes worker ownership, **not** event-source authenticity, tenant authorization or permission for customer IDs in payloads. Explicitly customer-tagged invoice and payment steps now get the narrow owner check described in the Phase 2 handoff; unsupported tagged event types are held. A workflow task's `customer_id` is not automatically a customer execution scope in the executor. Configuration and grant checks are snapshots, not revocation/effect fences. All event producers and customer-scoped workflow definitions need independent review. |
| `customer.account_assistant` | POST `/account/ai/assistant` authenticates the current account; `actorUserId` is derived from auth, not request body. | Dispatcher checks active actor; contract requires actor and customer match; executor rechecks customer scope and holds an active-account row lock through claim; tool gates still apply. | No proof of authorization after a claim or already-dispatched effect; customer account role and delegated-support policy need independent review. Customer claims require a transaction-capable handle. |
| `customer.website_launch` | Customer support route authorizes the conversation by account or visitor token; launch choice is server recognized; named actor is derived only if the authenticated account owns the conversation. | Dispatcher locks and rechecks AI-active conversation and named owner; attached lookup task and launch workflow are fenced, contract restricts anonymous to system/no customer scope. | Visitor-token possession is authority for the conversation, not verified customer identity; it does not prove cancellation of an already-started lookup or provider outcome. |
| `board.child` | Runtime handler calls `runChildAgent` under an already-running parent; server selects child agent, limits nesting and carries actor/customer scope. | Registry task admission, child task identity/key and executor/tool gates; reused child is not restarted. A persisted `board.child` cannot dispatch another child even when in-memory depth is absent. | Trusted in-process handler and inherited scope are assumed. The entry-point marker is not proof of parent provenance; legacy rows without it lack this guard. There is no separately persisted parent authorization proof or fence against later actor/grant revocation. |

## Local checks and open gate

`tests/integration/ai-entrypoint-authorization.test.ts` tests real routes with unauthenticated users, customers, staff and an admin demoted in the database (no task/run/event/report created); admin and super-admin pass authorization but fail malformed bodies before dispatch; an event is accepted after the database role is restored to admin and is attributed to that actor; and a customer-supplied actor/customer/entry-point spoof does not alter authenticated customer scope. Other contract, customer isolation, workflow, visitor-access and PostgreSQL tests remain documented in the Phase 2 handoff. These checks do not exhaust every role, producer, concurrent revocation or deployment configuration.

**Still required:** independent review of every entry point and event producer, durable authorization/revocation design with real concurrency tests, customer-scoped workflow authorization semantics, effects already in flight, and review against the actual deployed schema. This inventory identifies risk; it does not approve the current authority model or close the Phase 2 gate.
