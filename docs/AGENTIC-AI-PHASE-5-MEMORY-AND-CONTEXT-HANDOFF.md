# Phase 5 — Agent Memory & Context: local work in progress

**Status: IN PROGRESS / gate not met.** Started at the user's direction without waiving incomplete Phase 2, 3 or 4 gates. This phase is the ten-phase Agentic AI memory/context phase, not the separately named historical commerce/billing Phase 5. No staging or production action is authorized by this work.

## Inspected surfaces and first local boundary

- `ai_memories` (migration 0066) has scopes, nullable customer/agent keys, JSON values and optional expiration; its coalescing unique index does not authenticate a caller. The repository originally allowed customer-scope reads/writes with a null customer ID, and the runtime exposed shared scopes to customer runs. There were no current handler reads, but customer profile wrote a health score under whatever `task.customer_id` happened to contain, even when null. These are code-level risks; this work does not establish that a leak occurred.
- `runtime/memory-policy.ts` now denies all runtime memory reads and writes for customer-requested or customer-attributed tasks, and denies customer-scope memory for all runtime tasks. The customer-profile handler still computes and returns its existing result but no longer stores a health-score memory. Internal tasks with null customer attribution can still use non-customer scopes. This is a temporary fail-closed compatibility restriction: affected future handlers or customer-attributed board tasks that request memory can fail; there is no customer personalization or cross-conversation memory capability from this change.
- Repository single-record reads and writes require a non-null, non-sentinel customer ID for customer scope and disallow a customer ID in other scopes. This is input consistency, **not authorization**: trusted direct repository callers can name another real customer. Existing malformed rows are not deleted or repaired; the database schema is unchanged and direct SQL/listing can bypass these guards.
- Board overview now ignores expired executive digest rows and customer-attributed legacy rows. Expiry filtering does not physically delete a row, and other direct queries and listMemories must be independently reviewed. Sweeps only prune records with an explicit expiration; null expiration is indefinite.

## Scope and unresolved privacy risks

Support conversations, messages and previous-message context (`src/routes/ai-support.ts`, `src/services/ai-support-operator.ts`) are separate stores and are not governed by the new memory policy. Existing authorization uses account ownership or visitor-token possession, and retrieval reads the last eight messages of the selected conversation; no new cross-conversation context was introduced. Conversation, task/run inputs and results, support analytics, knowledge sources, board output, audit data, backups and provider-side data need a complete data-flow and authorization audit. Tasks not marked with `customer_id` can still contain customer information in input or outputs and can access shared runtime memory; the restriction is not comprehensive information-flow control. Redaction is key-name based and does not guarantee removal of secrets or sensitive text in strings. Historical data is unchanged.

No retention/deletion policy, consent mechanism, customer-access/deletion endpoint, encryption design, secret detection, data-subject export, backup deletion, or purpose/audience labels have been implemented. Deletion must be designed alongside audit and workflow foreign-key/retention requirements, including migrations 0110–0113; no records should be purged merely on the basis of this local change. The existing expiry sweep, in isolation, is not a retention policy. No migration or public API was added.

## Follow-up: support-question model disclosure boundary

The public conversation route previously left `allowModel` implicit, and the support decision layer interpreted omission as permission to use the website-builder model when configured. In that path, the current customer question is placed in a model request; configuring a model for another feature alone is not a support-specific privacy decision. The public support route now explicitly disables optional model phrasing, and the decision layer defaults to disabled unless an internal caller explicitly passes `allowModel: true`. The admin knowledge overview and page report deterministic support phrasing even when a model is configured for other uses. This intentionally changes behavior for deployments that relied on model-rephrased public support answers.

This is a narrow outbound boundary, not an authorization/consent system: the internal opt-in is not itself an authorization check, other model consumers are unchanged, and current and earlier conversation messages remain stored and used locally for support, retrieval and human handoff. Existing transcripts, logs and provider-side data are not deleted. Prompt injection, unrecognized sensitive text, retrieval/audit logging, other outbound integrations and deployment configuration still require review. No model endpoint was contacted.
