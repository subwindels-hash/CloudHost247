## Reviewed-proposal binding

The existing approval route required an authenticated administrator, a one-winner decision and a transactional audit, and rechecked permissions before claiming execution. However, the inbox did not show the stored `arguments` (it looked for a non-existent `preview`), and a decision submitted only an ID. A changed proposal between viewing and deciding could therefore be approved without the operator seeing the new content. This is a code-level risk, not evidence that a real approval was changed or misused.

The permission-gated approvals list now returns a SHA-256 review fingerprint over the stored proposal identity, agent/task/run, action/tool, arguments, evidence, reason, risk, affected customer/resource and expiration. Canonical JSON key ordering avoids false changes from object key order. The decision API requires the fingerprint for both approval and rejection, locks the approval row and compares the proposal before making the transactional decision and audit; a stale review returns conflict without a decision or action. The immediate execution path compares the claimed proposal to the same submitted fingerprint before dispatch. The inbox displays the stored proposal details and requires an explicit review checkbox before either action, and no longer claims that a successful tool response proves a downstream outcome. Existing authorization, single-use claim, expiry and audit checks remain. The initial fingerprint change added no migration or new tool; the subsequent preservation change below adds migration 0114.

**Important limitations:** The fingerprint is an unkeyed stale-review detector, not a signature, authentication, consent proof, or tamper-proof durable approval record. It is supplied by the authorized caller, not stored with the decision; trusted code/direct SQL can bypass these checks, and a privileged or malicious caller can compute a new fingerprint. Expiration is normalized to JavaScript millisecond precision for the fingerprint, while the DB independently checks the actual expiry. Only the explicitly listed proposal fields are bound; agent/tool policy, underlying resources, customer status and ownership, external state, authorization grants or approval rules may change after checks. The post-claim check uses the claimed snapshot and does not fence changes/revocation or external effects after that check. It does not bind genuine customer consent, verify provider outcomes, implement a durable execution token, or make execution/audit atomic with effects. A lost commit or post-effect audit failure is uncertain, never a reason to retry blindly. Redaction still misses secrets embedded in strings, and existing audit/invalid-input paths may persist free text; the preservation check is not a privacy filter. The existing staff/admin approvals list remains sensitive and needs its own privacy/retention review.

This is an intentional API compatibility change: old clients omitting `reviewFingerprint` receive validation failure, and old UIs should not be used to make decisions. Mixed-version server/UI rollouts and old workers are not proven safe and require separate review. Existing pending approvals have no original-argument provenance and cannot be approved by the updated path; administrators can reject or investigate them. No staging or production migration or deployment has occurred.

## Argument preservation follow-up

Migration `0114_ai_approval_argument_integrity.sql` adds a default-false `arguments_verified` flag. The updated runtime only marks a newly created approval verified after checking that validated arguments equal the raw request and equal their storage-redacted representation; trimming, coercion, stripped keys, truncation and redaction therefore fail closed rather than silently changing the proposed action. Top-level marker strings are also rejected; marker matching is only a precaution, not proof of provenance or comprehensive secret detection. The denial audit for this preservation failure omits the arguments. Execution repeats the preservation check and requires the flag; the decision route blocks approval of unverified proposals but allows rejection. The review fingerprint includes the flag, and the UI explains the distinction and disables approval for unverified rows.

Existing rows default to unverified, including already approved or executing records. Do not backfill them to true: original input cannot be reconstructed from stored values. Investigate approved/executing/unknown outcomes rather than replaying; pending rows can be rejected and re-created from a fresh request. This flag is a trusted-code assertion, not cryptographic or immutable provenance; direct database writers and old application versions can bypass it. Deployments must review migration ordering and prevent mixed-version decision/execution workers before using this feature. No database outside the disposable local tests was migrated. The check can reject formerly accepted requests, including schema normalization and overly long content, and is not a general privacy or authorization solution: short free-text secrets can still be stored and disclosed, including in other existing audit paths.
