# Google Analytics 4 — integration and limited server-side purchase delivery

**Incomplete and not production-verified.** This implementation can send `page_view` on an explicit set of public routes, `contact` after a successfully persisted Node contact form submission, and selected catalog `view_item`, `view_item_list`, `select_item` and `search` events, with explicit analytics consent. The Node manual-payment purchase sender is preserved but **disabled in code** due to an unresolved consent/dispatch race; broader ecommerce and cross-platform purchase coverage are incomplete. Local checks do not establish Google receipt or legal compliance.

## Create and configure a property

Follow Google's instructions to [create a GA4 property and web data stream](https://support.google.com/analytics/answer/9304153) and [find the Measurement ID](https://support.google.com/analytics/answer/9539598). In **Admin → Marketing Integrations → Google Analytics** (`/admin/marketing-integrations/google-analytics`), save the property name, hostname without scheme or path, and `G-XXXXXXXXXX` ID. Test checks syntax only. The last successful local validation shown is scoped to the current saved revision; it does not establish Google receipt and older audit entries without a recorded revision are not counted. Reset disables and removes the settings; audit history remains. Test mode sets `debug_mode` on manually sent page views.

**Before enabling**, an authorized administrator must inspect the Google web stream and disable enhanced measurement, particularly history-based page views, search, form and other automatic measurement. Also disable user-provided data capabilities in Google tag settings and user-provided data collection (including automatic detection) in the Analytics property, and review all connected destinations. Google notes that disabling property processing alone may not stop the tag collecting data: see its [user-provided data collection documentation](https://support.google.com/analytics/answer/14077171) and [Google tag settings](https://support.google.com/tagmanager/answer/12131703). These settings are controlled in Google, not by CloudHost247. Both checkboxes are operator attestations, not technical verification. Previously enabled configurations without the new user-data review fail closed until an authorized admin reviews and saves them again. Audit existing GTM containers, plugins and server-injected tags for duplicates and PII. Obtain legal review for applicable countries, especially cross-border transfers and consent. A different external Google tag or GTM container detected before initialization prevents this integration from loading, but late or hidden tags cannot reliably be detected. See [Google's manual page-view guidance](https://developers.google.com/analytics/devguides/collection/ga4/views).

Configuration is stored in the existing `marketing_integrations` table with revision conflict checks and transactional audit entries. The API requires a bearer token and a current admin/super_admin role, not a cookie session. The GA4 settings screen displays the latest 50 configuration saves, resets and local tests, including the actor ID and timestamp. Its `GET /api/v1/admin/marketing-integrations/google-analytics/audit` response is private/no-store and deliberately excludes request IPs, user agents and audit metadata; it is not an event-delivery log. Migrations `0090`, `0091` and `0092` add the provider, checkout attribution and purchase-delivery schema. Apply all three through existing migration procedures before deploying the updated application; consent updates require the new schema. No Google service-account key is used.

## Scope and privacy behavior

The Node React shell imports `shared/site/marketing.js`; both Smarty themes include synchronized copies when their verified same-origin Node mount is configured. An explicit, current analytics preference is required; marketing consent is independent. No Google library loads before consent. The runtime disables automatic config page views, sends a single manual initial view and manual subsequent navigation views, and uses the configured ID. The allowlist includes the current fixed public SPA marketing/legal routes and fixed WHMCS public registry pages, plus a few existing public aliases and reviewed service-plan pages: 168 exact paths in `GA_PUBLIC_PATHS`. It is not generated at runtime, so new routes require review and an explicit update; account, admin, checkout, dynamic, query-string and fragment URLs are not. Google is unloaded by a page reload when navigating from a measured SPA page to an excluded route. Node installations mounted at non-root paths may need a deliberate allowlist extension. Traditional WHMCS pages only work when the shared theme script, matching hostname, same-origin Node mount and deployment CSP are correctly installed. Theme script URLs were versioned to avoid stale cached copies. Local tests simulate theme loading; no licensed WHMCS site was run. Other applications and unlisted routes are not covered.

Manual events use a fixed title and empty referrer rather than user-supplied content, and never include URL query strings. Stale SPA route callbacks cannot initialize or dispatch GA4 for a different current pathname. Pending SDK load/error callbacks cannot resume tracking after a withdrawal has started. These controls do not audit Google-side automatic collection, linked destinations or other third-party tags; stream configuration and real network inspection remain essential. On withdrawal the browser sets Google's `ga-disable-*` flag immediately, attempts to delete visible `_ga` cookies, and reloads to unload the SDK; other tabs fail closed and reload. Pages frozen in the browser back-forward cache suspend GA4 and reload on restoration before tracking resumes. Configuration is rechecked when a tab becomes visible and approximately every 30 seconds while active, so an administrator's disablement is **not instantaneous in an already open tab**. The runtime rejects missing, invalid or expired consent timestamps, checks expiry on every GA4 dispatch, and schedules a stop/reload at expiry; when a throttled background tab returns to visibility, it checks expiry before the network refresh. Browser clocks, throttled or frozen timers, storage failures, network requests already in flight and third-party tags outside this runtime are not controllable by this code, so an SDK unload may be delayed while the browser is suspended. Consent is stored by the existing 180-day preference manager, with accept, reject, customize, withdraw and reopen controls. No Consent Mode is implemented; rejection never permits cookieless analytics pings.

## Limited Node server-side purchase delivery (hard-disabled)

**Hard stop:** purchase client-ID capture, enqueue and dispatch are disabled in code, regardless of environment flags. Do not configure staging secrets or attempt Google verification yet. The preserved legacy sender has an unresolved withdrawal race; a separately reviewed coordination design and code change are required before enabling it. See the [staging evidence](./GOOGLE-ANALYTICS-4-STAGING-EVIDENCE.md).

The following describes the preserved legacy path, not currently active functionality. This is an implemented but **not externally verified** slice, not complete ecommerce coverage. Only staff-confirmed **manual** Node payments qualify. Sandbox, Stripe/Paystack/PayPal and other unreviewed gateway modes, WHMCS purchases, taxes/discounts, unknown products and mismatched or unsupported currency/values fail closed. Some gateway initiators in this repository are mock implementations; a signed webhook alone does not establish live payment mode. Node/WHMCS do not share a verified transaction identity, so cross-platform deduplication is not established. No old orders are retroactively queued.

After explicit current analytics consent and only on an approved public route, the shared runtime asks the official tag for `client_id` with `gtag('get', ...)`. It posts the result to the same-origin consent endpoint using the HttpOnly consent cookie and CSRF header; the backend validates format, current consent revision, host, configuration revision and server-side purchase enablement. A browser is untrusted: format checks cannot cryptographically prove an ID came from Google. No identifier is synthesized when the callback never arrives. The client ID is encrypted using the existing credential keyring, associated with the consent session and copied into an authenticated Node checkout's context. If capture is delayed until after checkout, no purchase is attributed. A later consent decision increments a revision so an old in-flight capture cannot recreate a withdrawn identifier.

The staff-confirmation transaction queues only validated paid orders; a separate worker claims each order at most once. Before dispatch it rechecks the paid state, consent, matching configuration, real encrypted ID, supported currency and item/value reconciliation. It sends the actual order UUID as `transaction_id`, actual currency and item-based value, and fixed coarse item identifiers, but no customer name, email, URL, provider reference or plan text. Advertising user-data and personalization consent are denied. The payment must have completed within the preceding 72 hours; no event timestamp is supplied, so reporting reflects dispatch time, not necessarily payment time. Google's attribution may be limited when related browser and server events are separated by more than 48 hours.

**Delivery safety:** an order-keyed outbox tombstone is retained indefinitely alongside financial records to prevent local repeat attempts. HTTP 2xx means `http_accepted`, not validated or reported in GA. Timeout, non-2xx or a crash after a claim is `unknown`; these are not retried automatically because Google idempotency/receipt cannot be established. A stale sending claim becomes `unknown` after its five-minute lease. This favors avoiding double-counts over delivery guarantees. Do not reset tombstones or replay unknowns without a separately reviewed reconciliation process. The current admin UI does not display purchase outbox status; worker logs report aggregate counts only. A consent withdrawal cancels queued work, marks claimed work unknown until the same worker establishes its outcome, and deletes identifiers. The final check prevents dispatch when withdrawal wins before that check; an already-sent request cannot be retracted and the race between the final check and a network request remains and can be prolonged if the worker is suspended. A separate-process PostgreSQL test reproduced dispatch after withdrawal had committed when the worker had already passed its final check; strict no-new-dispatch-after-withdrawal is not certified. If the worker later receives a response for its claim it can record the HTTP status, without implying Google processed the event. The same limit applies to concurrent refunds/config changes. Terminal outbox attempts clear their checkout identifier, while session-linked browser IDs and remaining checkout contexts are deleted on withdrawal or when expired consent sessions are pruned by the worker (normally 180 days, cleanup may lag). Order/payment UUID tombstones remain linkable personal data; review retention and access with privacy/legal teams. Database backups follow the deployment's retention policy.

## Events and ecommerce

`page_view`, `contact`, a restricted `view_item`, catalog `view_item_list`/`select_item`, and a limited `search` are implemented. The `/search` page filters locally; pressing Search with at least two characters emits a consent-gated search action, not an event for every keystroke. The event uses the literal `search_term: "[not collected]"` rather than transmitting the actual query. It is an aggregate action indicator, not a report of search terms. Search elsewhere, including domain search, is not tracked. The list event is emitted after the `/hosting`, `/pricing` or `/offers` catalog loads and contains only known allowlisted item IDs actually present in the response. Their fixed list IDs are `hosting-catalog`, `pricing-catalog` and `offers-catalog` respectively. Selection is emitted when a visitor opens an available product’s plans; closing them is not a selection. Unknown identifiers, names, prices and currencies are omitted, and repeat list renders are deduplicated per page visit. `view_item` is sent only after a successful available matching catalog response on `/hosting/web-hosting`, `/hosting/vps`, `/hosting/dedicated`, `/hosting/cpanel`, `/hosting/business`, `/hosting/wordpress`, `/hosting/reseller`, `/hosting/windows`, `/hosting/email`, `/hosting/ssl`, `/cloud/public` or `/cloud/private`; the `/web-hosting`, `/vps-hosting` and `/dedicated-server` legacy aliases are also allowlisted. Each path only accepts its fixed matching product slug. Its `items` array contains only `item_id`; no price or currency is inferred for a product group. Repeat renders on the same page visit are deduplicated, and an unavailable or failed catalog response does not fire it. The public `/service-plans` index sends `view_item_list` for recognized, available product groups after the catalogue loads, using `service-plans-catalog`; clicking an available product’s “View plans” link sends `select_item`. The twelve corresponding exact `/service-plans/catalog/<fixed-product-slug>` pages send `view_item` only after the returned product matches that slug and is available. This is group-level rather than plan-level measurement; no plan, user, price or currency data is sent. Six exact public platform-plan detail pages (`/service-plans/platform/website_builder`, `/ai_builder`, `/online_store`, `/marketing`, `/inbox`, and `/logo_maker`, all under that same platform prefix) can send a coarse `view_item` for their fixed service category only when the public API returns at least one matching published plan. The fixed item IDs are `platform:website_builder`, `platform:ai_builder`, `platform:online_store`, `platform:marketing`, `platform:inbox`, and `platform:logo_maker`; plan identifiers, names, prices and currencies are not sent. The platform links on the index are not tracked as a list or selection because the index does not establish whether plans are published. Unknown product or platform paths, unavailable items, query/fragment URLs and failed loads are excluded. On the canonical WHMCS theme’s `/cloudhost247-hosting.php` page without a query or fragment, a successfully rendered available-product catalogue can emit `view_item_list` for only the distinct coarse categories `whmcs-hosting`, `whmcs-vps`, and `whmcs-dedicated`. Clicking “Configure in WHMCS” can emit `select_item` for the chosen product’s category, not its individual plan or ID. The list ID is `whmcs-public-catalog`; no name, price, currency, destination URL or customer data is sent. Empty, failed, filtered-query and unsupported/legacy-theme catalogues are not tracked, and the click does not mean cart addition or purchase. This is category-level measurement, not a product-level or revenue report. Other WHMCS product events are not covered. The Node contact event fires only after the contact API confirms persistence, only on `/contact`, and sends no form fields, event IDs, or user-supplied parameters. It is independent of Meta marketing consent and is not queued until consent is granted. Failed or unconfirmed requests produce no event. These support/billing/legal contacts are not automatically classified as sales leads; `generate_lead` is not emitted. WHMCS contact form tracking is not implemented. A limited manual-payment Node `purchase` sender is described above. Signup, login, cart, domain-search, lead and other events are not implemented. Existing Meta event and receipt logic is separate and must not be treated as GA4 coverage. Future ecommerce needs authoritative successful payment records, actual transaction currency and value, analytics-specific consent, privacy-safe item data, and Node/WHMCS cross-channel deduplication. Pending orders must not trigger purchase. See Google's [event reference](https://developers.google.com/analytics/devguides/collection/ga4/reference/events) and [ecommerce guide](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce).

## CSP and verification

Node Helmet remains enabled. For this limited no-ads setup, `script-src` permits `https://www.googletagmanager.com`; `connect-src` and `img-src` add that origin and explicit `https://www.google-analytics.com` and `https://region1.google-analytics.com`. No unrestricted wildcard or inline script was added. Google's [CSP guidance](https://developers.google.com/tag-platform/security/guides/csp) describes additional host patterns; these are intentionally not enabled here. Regional delivery, deployments using other Google endpoints, and equivalent WHMCS/proxy CSP must be validated in staging. Never weaken CSP broadly to make the test pass.

With consent and stream settings reviewed, use Google's [Realtime](https://support.google.com/analytics/answer/9271392) and [DebugView](https://support.google.com/analytics/answer/7201382) and browser network inspection to check the right property, safe payloads, one event per navigation, rejection, withdrawal, disabled state and CSP. Local script load or a configuration test is **not** provider receipt. No live property, production CSP, deployed WHMCS, Google network payloads or provider receipt were verified in this work.

If settings fail to load, apply migration 0090 and check admin role and API routing. If the tag does not appear, check the exact hostname, enabled setting, analytics consent, public route allowlist and conflicting tags. If the SDK loads but no data appears, review CSP and Google stream settings; avoid changing the consent decision or adding a second tag as a workaround.
