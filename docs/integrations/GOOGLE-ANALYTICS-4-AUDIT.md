# GA4 repository audit and conventions log

Date: 2026-11-08. Audit precedes implementation. This is a repository audit, not a production deployment or tag inventory.

## Structure and existing implementation

The repository contains the WHMCS PHP site and Smarty themes (`templates/cloudhost247`, `templates/cloudhost247_legacy`, order forms and addon modules), the independently deployed Fastify/React platform (`cloudhost247-node`), another independent `platform` application, shared site assets, infrastructure and tests. Customer-facing entry points include the React router and layouts, both Smarty theme footers, and tools/static builds; not every application is automatically covered by the same shell.

- `shared/site/marketing.js`, `marketing.css`: canonical shared Meta browser engine and cookie preference UI; the same JS is copied into both theme `js/marketing.js` files. React imports the shared file via `frontend/src/lib/marketing.ts`. Smarty includes it via `templates/cloudhost247/includes/marketing.tpl` and `templates/cloudhost247_legacy/footer.tpl`, only when a verified same-origin Node mount is configured.
- `cloudhost247-node/src/marketing/*`, `src/routes/{marketing,admin-marketing}.ts`, migration `0089_create_marketing_integrations.sql`: canonical Meta settings, server-side consent (180 days, opt-in, distinct analytics and marketing flags), audit history, event validation, authenticated verified-purchase receipt and CAPI delivery. Meta's Purchase is tied to successful payment, not order creation. Existing consent preferences support accept/reject/customize/withdraw and same-tab/cross-tab updates; analytics is currently an unused category.
- `frontend/src/pages/AdminMarketingIntegrationsPage.tsx`, `frontend/src/lib/marketing-admin-api.ts`, `frontend/src/App.tsx`: admin console and protected route. Admin routes use `requireRole` for admin/super_admin, `recordAudit`, optimistic revision and existing bearer-token API conventions. Mutation and bootstrap consent routes enforce origin and consent-bound CSRF; examine existing auth behavior rather than introduce a conflicting CSRF scheme.
- `cloudhost247-node/src/plugins/security.ts`: Helmet CSP enabled, same-origin plus narrowly scoped Meta origins. Google is not permitted. WHMCS server CSP is deployment-specific, not centrally specified by this file.
- `frontend/src/lib/usePageMeta.ts`, Smarty headers, generated `shared/site/content/*`: SEO and canonical metadata. No checked-in GA4 or GTM tag/configuration was identified by repository searches; deployed templates, WHMCS addons, GTM containers and external reverse proxies still require inventory before enabling.
- `cloudhost247-node/tests/integration/marketing-*`, `frontend/tests/unit/shared-marketing-engine.test.ts`, `admin-marketing-integrations.test.tsx`, and `tests/marketing/session13.php`: conventions and regression coverage. `docs/integrations/META-PIXEL-*` documents Meta deployment caveats.
- `cloudhost247-node/database/migrations/0040_create_platform_settings.sql` exists, but `0089` is the dedicated marketing integrations store. Its provider and Meta-only check constraints prevent inserting a GA4 row unchanged. An additive migration must preserve Meta constraints while adding provider-specific validation; never alter applied migrations.

## Gaps and planned architecture

There is no GA4 configuration, official Google tag loader, analytics-aware runtime or Google CSP allowlist. The existing Meta receipt requires *marketing* consent and its Meta-shaped data is not automatically a safe GA4 purchase source. WHMCS payment authority and cross-platform deduplication are not established. Event payloads and URLs can contain personal information; analytics must use explicit allowlists and avoid query strings and sensitive paths. A configured ID is not proof of delivery or Google property access. A deployed GTM configuration may create duplicates beyond what this repository can detect.

Recommended: extend the existing marketing table with a provider-specific GA4 row via additive migration; provide RBAC-protected, validated, revision-checked and audited admin operations; add a minimal public configuration to the existing consent bootstrap. Extend the single shared runtime and existing analytics consent flag, not a competing consent manager. Emit explicit page views with automatic page view disabled, sanitize URLs, and ensure withdrawal stops dispatch. Use server-authoritative payment receipts only when analytics consent, ownership, currency, transaction and cross-channel deduplication can be proven. Avoid falsely claiming realtime receipt; external GA4 property/DebugView and deployment CSP are required. Update Google-only CSP sources minimally after reviewing Google's official documentation.

Planned files: additive migration; `src/marketing` GA4 configuration service/schema; admin and public marketing routes; admin React page and navigation; shared browser engine plus synchronized Smarty copies; `security.ts` if tracking is enabled; relevant integration and browser tests; this audit and `docs/integrations/GOOGLE-ANALYTICS-4.md`. Scope may be reduced if verification or a safe cross-platform implementation is blocked; record actual results and outstanding work rather than implying completion.

## Conventions

1. Node PostgreSQL is the only configuration authority; no GA service-account secret is needed.
2. Admin changes: existing `requireRole`, transactional audit, revision conflict detection, strict schemas and bearer authentication. Public bootstrap: minimal allowlist, no admin diagnostics, no-store.
3. Shared consent is authoritative, deny by default; never infer consent from authentication or checkout. Do not change Meta semantics or existing tables in place.
4. Never treat local validation, tag load, or browser dispatch as Google receipt. Verify deployed GTM/other tags and regional privacy rules with operators/legal counsel.
5. Ship testable, fail-closed slices and explicitly document unimplemented functionality and limitations.
6. When the privacy review expands to a distinct Google-controlled collection capability, require a separate explicit attestation; older enabled records lacking it fail closed rather than silently inheriting a new assumption. Attestation is not verification.
7. Public page coverage uses a finite fixed-path allowlist, never a route prefix or runtime CMS expansion. A route-inventory regression test forces review if the public registries change. Do not add customer, unbounded or query-bearing routes without a dedicated privacy design.
8. Runtime analytics grants must include a valid unexpired server-provided expiry; dispatch checks cannot rely solely on periodic refresh. A browser timer is best effort and cannot guarantee SDK unloading while suspended or undo in-flight requests.
9. Configuration tests are local syntax checks, not Google verification; show successful checks only against the exact configuration revision. Admin audit views are role-gated and expose no IP address, user agent or raw audit metadata.

10. WHMCS public catalogue interaction markers are present only in the canonical theme; suppress the marked root for an error or empty list. Emit fixed coarse category IDs only for the query-free public catalogue and never derive event payloads from product names, IDs, links, prices or customer content. The Configure click indicates selection, not cart addition or purchase. Rendered Smarty/WHMCS behavior remains a staging verification requirement.

11. The public service-plan index and twelve exact catalogue-group detail paths are separately reviewed; never accept dynamic route slugs as analytics identifiers. Require a successful matching available product response for detail views and available catalogue entries for list/selection. At that point platform plan paths, prices and customer/cart routes remained excluded.

12. Six exact public platform-service plan paths are now reviewed separately: send only their fixed service-category ID after a successful public response contains a matching published plan. Do not send plan IDs, names, prices, currencies or customer data; the unpublished platform links in the index do not establish availability and must not create list or selection events. Unknown platform paths and customer/cart/editor routes remain excluded.

13. Node order checkout stores a minimal analytics-only consent association only when the server-observed hostname, GA4 settings and current explicit analytics preference all pass; it rechecks configuration revision and consent with row locks before insertion. The association is pseudonymous personal data, not anonymous; it has no URLs, payment values, browser IDs or contact details, and is removed on analytics withdrawal and when expired consent sessions are pruned. Re-consent is not retroactive. Attribution storage is best-effort and sends no purchase event. Migration 0091 must be applied before code using the consent service is deployed. WHMCS attribution and a cross-platform transaction identity remain unresolved.

14. A non-exported-over-HTTP, read-only GA4 paid-candidate helper provides fail-closed checks and fixed-point line reconciliation for staff-confirmed manual Node payments with an active analytics checkout association. It excludes sandbox, unreviewed gateways, unknown items and nonzero tax/discounts. Its result is not proof of external provider receipt, an event, an idempotency claim, or authorization to send: the sender must recheck under a race-safe delivery design. No GA4 client ID or API secret is collected by this helper.

15. Subsequent purchase-delivery slice: keep the paid validator separate; capture only a consent-revision-bound browser client ID encrypted server-side; bind Measurement Protocol credentials to the configured stream and opt in separately; queue confirmed eligible manual payments in an order-keyed tombstone; recheck immediately before one local attempt and treat all ambiguous outcomes as unknown. Do not claim Google receipt, WHMCS cross-platform deduplication or reviewed live gateways without external evidence. See the runbook for retention and the unavoidable in-flight race.
