# Google Ads integration audit and implementation plan

Audit performed on 2026-11-08. This repository has a Node/React platform plus a separate PHP/WHMCS surface. The Node platform is the canonical integration owner; no new parallel tag manager or consent store should be introduced.

## Missing functionality

No Google Ads destination/configuration, conversion-action map, Ads tag delivery, linker, Google Consent Mode v2, Ads diagnostics, Google-specific admin API/UI, CSP allowlist, or Google Ads operational guide existed. Analytics consent existed, but the legacy GA4 and GTM snippets executed unconditionally in the theme head and were not coordinated with it. The existing Analytics and GTM IDs are WHMCS theme settings; they are not configured in Node. WHMCS remains an external billing authority in production and no verified WHMCS payment-confirmation callback was available to connect from this checkout.

## Proposed slices and conventions log

1. **Configuration and administration** — add Google Ads as a distinct provider in the existing marketing integrations table; strict schema validation; admin-only API, revision checks, audit trail, test status, and dedicated `/admin/integrations/google-ads` route. No credentials or invented IDs.
2. **Consent-aware browser delivery** — extend the existing shared runtime with the official Google tag (`gtag.js`) only when Ads is enabled and ad consent is granted; establish default Consent Mode v2 signals before tag load; update signals on changes/withdrawal; linker via the Google tag; no second banner.
3. **Conversion mapping** — adapt existing successful commerce and backend-success lead event calls to separately configured Ads conversion labels; preserve verified purchase receipt values/currency/transaction identifiers; avoid generic view/click-as-conversion behavior and duplicate dispatch.
4. **Security, tests and docs** — minimal CSP changes, schema/runtime tests, privacy review, and Google account setup/troubleshooting documentation. No server-side Ads API upload is enabled without reviewed credential scope, encryption and operational need; browser tag plus verified receipt is the initial supported path.

## Implementation outcome

Slices 1–3 and the documentation/security portion of slice 4 are implemented: Google Ads has a separate provider row and admin API/UI, the shared React/Smarty runtime gates Ads/GA4/GTM/Baidu behind the existing preferences, Consent Mode v2 defaults precede Google/GTM scripts, and verified browser purchases use the existing authenticated paid-invoice receipt. The generated WHMCS runtime copies were regenerated. Existing GA4 settings stay in WHMCS and are not copied into the Node configuration. The existing GTM container now loads only with both analytics and marketing consent; individual GTM tags still require correct built-in consent settings.

Not implemented/verified: Google Ads API/server-side uploads, enhanced conversions (intentionally disabled pending privacy/legal review), dynamic remarketing/feed/campaign support, external Google account linking, subscription/renewal/upgrade event triggers not present in an authoritative workflow, WHMCS payment-completion conversion hooks, live account/tag verification. The legacy PHP `platform` API origin/CORS and WHMCS consent-cookie deployment must remain same-site/reverse-proxied as required by the existing shared API; no production environment was available to prove this.

Conventions: provider config persists in `marketing_integrations`; secrets (if any) are separate encrypted records; admin changes use existing role checks and `recordAudit`; public DTOs are allowlisted; consent decisions remain owned by the existing manager; `trackMarketing` is invoked only after successful business operations; receipt is the only Node purchase authority; Google account linking, conversion-action creation and primary/secondary classification remain externally completed and are never claimed as verified by local configuration tests.
