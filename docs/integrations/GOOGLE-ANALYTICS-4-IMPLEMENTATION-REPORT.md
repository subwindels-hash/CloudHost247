# GA4 implementation report — including limited Node purchase delivery

Date: 2026-11-08. **Incomplete and not production-verified.** A limited Node manual-payment purchase path is implemented but Google acceptance, cross-platform deduplication, other gateways and most remaining standard events are not verified or implemented. No live Google property or deployed WHMCS environment was tested.

## Main-branch reconciliation (local only)

The shared runtime coordinates one first-party Google tag library for GA4 and Google Ads. GA4 is configured only with current explicit analytics consent, an approved public route, and the managed GA4 configuration; Ads is separately gated by marketing consent, with destination-specific event routing. GA4 rejects detected unowned Google tags. Legacy theme GA4/GTM options are suppressed when the managed analytics configuration is present to avoid competing owners; legacy Baidu remains separate. Google-side linking, automatic collection and real network behavior remain unverified; this is not staging certification.

Migrations 0090–0092 on main remain untouched. The not-deployed GA4 migrations are renumbered 0093–0095 and preserve the Meta, Ads and TikTok provider constraints. Existing deployments that independently applied the earlier GA4-numbered branch require explicit reconciliation and checksum review, not automatic renumbering. Purchase delivery remains non-configurably hard-disabled; the legacy withdrawal race is not fixed, no automatic replay is authorized, and no deployment or Google event has occurred. Before any future deployment stop and verify all old workers cannot resume; after deployment and restart verify the interlock remains disabled and preserve the existing outbox. Reactivation requires the previously documented independent architecture review and authorization.

## Completed slices

The repository audit and conventions preceded changes. The configuration slice provides admin/super-admin RBAC, strict ID/domain validation, revision conflicts, confirmed reset, transactional audit and an honest syntax-only test. The admin screen now shows the most recent 50 scoped audit actions and the last successful local validation for the current revision, explicitly not provider verification. Its read-only audit endpoint excludes IP, user-agent and raw metadata and requires a fresh admin role. No credentials are stored in the administrative configuration. A second slice adds a hostname-bound public bootstrap, operator stream-review attestation, GA4 enable/disable and test-mode settings, and a consent-aware shared browser page-view runtime. Analytics consent is distinct from Meta marketing consent. The runtime suppresses Google's automatic config page view, emits explicit manual page views, detects already-present GTM/Google scripts, restricts measurement to a static public-route allowlist without query/fragment data, disables on withdrawal and reloads to unload the SDK. Existing Node Helmet CSP was expanded with explicit Google hosts only. Smarty copies are synchronized. A contact-event slice adds a data-free `contact` event only after the Node contact API confirms successful persistence and only with analytics consent. No `generate_lead` is emitted for general support, billing or legal enquiries; WHMCS contact tracking is not implemented. A product-view slice records `view_item` for matching available catalog entries on twelve public product routes and three legacy aliases; only a fixed `item_id` is sent, with no inferred price or currency, and rerenders are deduplicated per page visit. A catalog-list slice adds `view_item_list` after the catalog loads on `/hosting`, `/pricing` or `/offers`, and `select_item` when an available product’s plans are opened; each route has a fixed list ID. Both transmit only known catalog identifiers; unknown values and all customer-provided content are filtered out. A site-search slice tracks explicit submissions on `/search` with a constant `[not collected]` search term instead of the user’s query. Other search surfaces are not covered. A server-rendering regression introduced by the catalog slice was identified and fixed by providing a fail-closed server snapshot. GA4 is suspended during back-forward-cache freezes and reloads on restoration; untracked cached pages resume configuration checks. Admin consent diagnostics now treat expired or outdated preferences as restricted. The runtime now rejects stale SPA route callbacks and prevents late SDK load/error handlers from undoing a pending withdrawal. A separate user-provided-data review attestation is required to enable GA4; old configurations without it fail closed. A subsequent page-view coverage slice expands the explicit allowlist to 149 fixed paths from the current SPA marketing/legal inventories, WHMCS public registry and existing aliases; query/fragment, private and dynamic paths remain excluded. Both Smarty script URLs are cache-versioned. GA4 additionally requires a valid unexpired consent timestamp on every dispatch, schedules expiry-based disable/reload, and checks expiry before refreshing when a background tab becomes visible. Timer throttling or browser suspension can delay unloading the SDK. The canonical WHMCS theme’s unfiltered public catalogue now emits consent-gated `view_item_list` and `select_item` for coarse, fixed hosting/VPS/dedicated categories only, when available items are rendered or their Configure link is clicked. These are not individual product, cart or purchase events; no product names, prices, currency or customer data are transmitted. Query-filtered catalogues and other themes/surfaces are excluded. A service-plan slice adds the public `/service-plans` list and available-product selections, plus matching available product-group views on twelve exact `/service-plans/catalog/<fixed-slug>` URLs. It sends allowlisted product-group IDs only, not plan details, prices or currency; unknown/dynamic product and platform-service paths were excluded in that slice. A further slice adds `view_item` on six fixed public platform-service detail paths, only after a matching published plan has loaded. It reports the fixed service category, never an individual plan, customer data, price or currency; index platform links are not tracked as selections. The public page-view allowlist now contains 168 exact paths; unknown platform paths and customer/cart/editor routes remain excluded. An additional Node checkout slice records a minimal pseudonymous order-to-consent association when GA4 is enabled for the request host and explicit analytics consent is current, independently of Meta. It rechecks consent and configuration revision under row locks, deletes associations on withdrawal, and cascades expiry cleanup. It records no browser ID or payment data and emits no checkout or purchase event. No WHMCS checkout context or cross-platform deduplication is implemented. A read-only paid-candidate builder checks current analytics consent, matching configuration revision, a staff-confirmed manual payment and reconciled paid invoice/order and coarse known items; it preserves actual currency/value and rejects sandbox, other gateway modes, unknown items and nonzero taxes/discounts. The builder remains independently read-only and does not itself produce an event or transaction ID; the separate sender now invokes it at queue and dispatch time.

### Latest slice: Node purchase delivery

A server-only opt-in requires a stream-bound Measurement ID, API secret and encryption keyring. The consented public runtime obtains a client ID using `gtag('get')`; a CSRF/same-origin endpoint checks consent revision and stores it encrypted. Checkout copies it to the order context; the manual payment transaction queues a separately validated candidate. A worker rechecks consent/configuration/payment, uses actual value/currency and the genuine Node order UUID, and posts to Google without exposing or logging the secret. A durable order-keyed tombstone prevents repeat local attempts; timeout, non-2xx and expired claims are unknown and are never automatically retried. Withdrawal deletes attribution, cancels queued work and records in-flight claims as unknown until a response is known; already-sent requests and the check-to-dispatch race, which can be prolonged by process suspension cannot be undone. Session identifiers are retained until withdrawal/expiry cleanup; terminal checkout snapshots are cleared. The browser cannot cryptographically prove the origin of a client-supplied ID. The admin interface does not show outbox diagnostics. No cross-platform deduplication or approved real gateway modes are established.

Verification for this slice: 67 focused GA/consent/Meta/migration integration tests passed; payment/webhook/commerce and GA/Meta config regressions passed 86 tests; a further synthetic duplicate signed Stripe webhook test confirmed unreviewed providers do not queue GA4 even with attribution (the first attempt lacked test process environment variables and passed after the fixture was fixed); full frontend suite passed 74 files / 957 tests; backend lint, frontend TypeScript, production build, diff/copy/syntax checks, 21 marketing and 23 website static tests passed. The first full frontend run was parallel with build and database-heavy tests and failed five unrelated UI waits; it passed in full when rerun without that load. PGlite concurrency coverage is not a substitute for multiple live PostgreSQL connections. Google network delivery, DebugView, property acceptance, deployment CSP and licensed WHMCS were not tested. **Do not mark the milestone complete until authorized synthetic nonproduction Google verification and remaining acceptance criteria are satisfied.**

## Final verification readiness — local PostgreSQL finding

An explicitly disposable local PostgreSQL 17.6 cluster and separate Node worker processes were used with synthetic credentials and a fake transport, never Google. The opt-in `ga4-purchase-postgres.test.ts` suite passed **6 tests**: one of six workers dispatched, a withdrawal committed before the final check blocked dispatch, an in-flight response was recorded after withdrawal, queued work survived worker replacement, and a killed in-flight worker was recovered as `unknown` without retry. The sixth test intentionally reproduced a remaining **internal acceptance blocker**: if a worker has completed its last consent check and is paused, it can start the transport after withdrawal commits. A paused process can extend that gap; therefore strict “no new dispatch after withdrawal” is not proven and should not be represented as merely an external staging dependency. Resolve/review the coordination requirement before certification. The local PostgreSQL migration run emitted nested BEGIN/COMMIT warnings from existing migration 0048; this test does not certify migration atomicity. The test suite's fake response is not Google acceptance. The opt-in instructions and safety constraints are in the [evidence record](./GOOGLE-ANALYTICS-4-STAGING-EVIDENCE.md).

## Consent/dispatch remediation decision — hard stop, not staging-ready

The requested strict ordering cannot be claimed from a database transaction alone: a worker suspended after its check may lose its database connection and lock, then resume and call the transport after withdrawal. A durable authorization barrier would preserve ordering but could require failing a withdrawal until an operator reconciles an uncertain worker. The user chose to preserve withdrawal availability by keeping purchase dispatch disabled. A non-configurable `isGa4PurchaseDeliverySafe()` hard stop now suppresses purchase ID capture, new queue entries and all worker dispatch even if both environment flags are enabled. The legacy implementation, consent revision, encrypted storage, outbox and validator remain in place. No coordination fix is claimed, and no new DB locks, migrations or lock timeouts were added. Existing sending rows cannot be safely replayed; mixed-version deployments and already-initiated network requests need explicit operational handling. This checkout has not been deployed.

Unmocked safety tests: two integration tests and five independent-process PostgreSQL 17.6 tests passed with fake transport only, including connection termination, restart, concurrent workers and withdrawal; six historical PostgreSQL enabled-sender tests are skipped. The 21 preserved delivery tests and five client-ID tests use a test-only mock to bypass the hard stop; they test legacy mechanics, **not** active dispatch safety. Together with the six unmodified paid-candidate tests, the focused four-file run passed 34 tests. Backend lint, frontend TypeScript, production build and `git diff --check` passed. The consent/checkout/Meta and shared browser runtime regression run passed 139 tests. No Google event was sent. Do not mark staging-ready until a separately reviewed coordination design addresses the race, lock/failure tests and external staging evidence. See the [evidence record](./GOOGLE-ANALYTICS-4-STAGING-EVIDENCE.md).
