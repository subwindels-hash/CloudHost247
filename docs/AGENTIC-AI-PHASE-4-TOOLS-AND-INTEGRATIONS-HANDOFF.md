## First increment: website-launch read-tool response contract

The existing, default-off website-launch workflow uses the registry-gated `lookup_launch_orderability` tool, a checksummed product map and the WHMCS catalogue/orderability client. Previously the handler validated the response only after the executor had persisted the full tool result and audit record. Malformed responses or extra upstream fields could therefore reach those records even though the customer-facing handler subsequently rejected them.

`runtime/launch-orderability-contract.ts` now validates and minimizes this one tool's result **before** it is returned to the executor for persistence. It checks the allowlisted category, recognized state/reason consistency, bounded product name, supported unique billing cycles, nonnegative decimal strings, consistent currency and HTTPS URLs without embedded credentials or fragments; unrecognized object fields are stripped. Mismatches and invalid shapes produce a generic `INVALID_CATALOG_RESPONSE`, without persisting the raw response. The handler applies the same contract again and checks the selected category. The customer copy now says prices and availability must be checked in the cart rather than claiming the cart was verified. The existing client has per-attempt timeout/retry configuration, and executor tool calls record duration; neither is a tested end-to-end deadline or proof of cancellation.

This is a local mocked adapter contract, not validation of a live WHMCS catalogue, billing cycles, cart behavior, authentication or payment. The result schema does **not** authenticate the cart host, prove the map is right, verify a cart or stop sensitive text in an otherwise accepted product name or URL query. Real cart URLs are constructed by existing map/config logic, which needs independent security and deployment review. The `checkedAt` timestamp records lookup completion, not necessarily when WHMCS was queried. Although the catalogue loader has a one-minute cache TTL, lookup duration, persisted results, and public HTTP caching mean this is not an end-to-end freshness bound; price and availability may be stale. No write tool, order, payment or provisioning was added. The checked-in map has zero bindings and 59 unmapped entries; no live provider was contacted.

## WHMCS transport response boundary

The shared WHMCS fetch transport previously called `response.text()` before checking string length, so its claimed 1 MiB cap did not bound the accumulated response and measured characters rather than bytes. It now reads the response stream incrementally, counts bytes, rejects declared oversized bodies early, cancels an over-limit stream without waiting for cancellation, and maps header/body timeout and stream errors to generic typed failures without retaining raw exception text. A real loopback HTTP test covers chunked oversized responses and a stalled body after headers; mock-stream tests cover UTF-8 boundaries, lying content lengths, cancellation, exact-limit behavior and sanitized errors.

This transport is shared by WHMCS reads, writes and session actions; no new actions or retry policy were added. A timeout or size error after a write or session request does **not** establish that WHMCS did nothing; never blindly replay an uncertain write. The cap bounds bytes accumulated by application code, not all buffering or allocations inside fetch/network stacks (a single delivered chunk can itself be large). The abort timeout applies per fetch attempt, not an end-to-end multi-call deadline, and depends on fetch/stream honoring its abort signal. Client read retries/backoff and the catalogue's multi-call path can exceed a single timeout; arbitrary custom transports are not bounded by this implementation. This is not proof of live WHMCS behavior.

## WHMCS action classification and envelope protection

The shared client previously trusted callers to label writes and session actions. An omitted/misleading flag could send an unrecognized mutating action as a retryable read, including in read-only mode. In addition, action parameters were appended after the authenticated envelope and could overwrite `action`, `identifier`, `secret` or `responsetype`. These are local code risks; no live exploit or exposure has been established.

The client now implicitly retries only the exact implemented read actions `GetProducts`, `GetProductGroups`, `GetCurrencies`, `GetClients`, and `WhmcsDetails`. `CreateSsoToken` requires its explicit session classification and remains single-attempt in read-only mode; session classification cannot be used to disguise other actions. Unknown actions are refused unless explicitly classified as writes and the existing full-mode guard allows them; explicit writes remain single-attempt. Parameter names are restricted to unambiguous ASCII identifiers, reserved envelope/authentication fields are denied case-insensitively, values are primitive, and a snapshot is used across retries so later mutation cannot change a request. Classification failures occur before the network.

**Limits:** full mode with an explicit write flag still permits an arbitrary syntactically valid action. This guard is not end-user authentication, business authorization, an action-specific write allowlist, consent, idempotency or reconciliation. Existing SSO is an intentional state-changing session exception in read-only mode, not a pure read. No new write endpoint or agent tool was added; downstream permission controls and review remain necessary. Introducing another WHMCS read requires adding and reviewing its exact action name. Old binaries do not have these checks. A timed-out write or session can have succeeded and must not be blindly retried.

### Further local hardening: installation matching and freshness wording

The shared orderability decision and direct cart builder now refuse bound product links when the map fingerprint does not match the configured installation; the public route reports `mapValid: false` without contacting WHMCS in that case. Configured cart and client-area paths reject traversal and empty segments, and the cart builder validates direct path inputs too. The launch response no longer promises a one-minute data-age bound. A fingerprint/checksum is not a signature, cannot detect a changed installation at the same URL, and does not authenticate upstream text; config and map still need operator review. Unmapped services can still report not integrated, and provider failures may take precedence in the shared decision. Config path restrictions may require operators to correct previously accepted paths.

Local mocked regression: seven focused files, 97/97 tests; server and script typechecks and `git diff --check` passed. No live WHMCS, deployment, browser end-to-end or full-suite verification was performed. Phase 4 and earlier incomplete gates remain open.

### Further local hardening: monetary completeness

Catalogue normalization previously converted missing, empty or negative setup fees to `0.00`, while accepting JavaScript number formats and malformed setup strings. It now requires an explicitly supplied, bounded nonnegative decimal for both the price and setup fee before offering a cycle; invalid or absent fees do not become zero. Hidden-product discovery now uses the same normalization instead of independently inventing setup fees. Public orderability and discovery may consequently omit otherwise valid WHMCS cycles when a provider omits setup fields; this conservative compatibility change requires validation against a real installation before enabling checkout. Explicit zero remains accepted. No provider calls or writes were made.

Local evidence: all 17 focused WHMCS unit and mocked orderability/SSO/launch integration files passed **290/290**; after adding a hidden-product regression, catalogue and discovery tests passed **24/24**. Server/script typechecks and diff check passed. These tests do not prove provider semantics or full-suite behavior. At the time of this increment the legacy single-pricing shape was still attributed without independent currency proof; the subsequent increment below changes that behavior. This increment does not close the Phase 4 gate.

### Further local hardening: currency attribution

Unkeyed legacy pricing was previously labeled with the requested currency (or USD when none was requested), even though neither established the currency of the amount. Normalization now leaves unkeyed amounts unattributed and unorderable; malformed currency keys and case-insensitive duplicate keys are also discarded rather than picking an arbitrary value. Currency-keyed prices for distinct valid codes remain usable. This applies to discovery as well as storefront/agent orderability; installs returning only an unkeyed legacy shape may report currency unavailable, and require provider-contract review rather than guessing a denomination. A currency key in an upstream response is still not independent authentication of the provider or proof that prices are current.
