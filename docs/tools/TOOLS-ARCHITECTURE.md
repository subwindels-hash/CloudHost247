# CloudHost247 Tools architecture and deployment

## Scope and ownership

The audited repository already contained the production Tools execution stack.
This change integrates it; it does **not** replace WHMCS or introduce a second
DNS/network engine. The registry has 68 entries: 64 executable tool surfaces and
four existing account portals. MRZ remains its independent existing module.
See the inventory for the preserved legacy PHP modules and their consumers.

- Authority: `cloudhost247-node/src/tools/catalog.ts`. `slug` is the stable ID.
  Names, descriptions, icon keys, canonical/legacy routes, API paths, categories,
  visibility, authentication, rates, cache policy, related tools, SEO titles and
  result mode originate here. Internal slugs and APIs were not renamed.
- Runtime: `core/registry.ts` combines operator settings, connected providers,
  capability probes, master/anonymous switches and immutable safety constraints.
  An ACTIVE override cannot manufacture a missing provider or system capability.
- Execution: the existing `routes.ts → core/executor.ts → handlers/* → services`
  chain retains auth, rate limits, abuse tracking, audit/history and caching.
  NS and CNAME reuse `dnsLookup`; domain WHOIS reuses Domain Services RDAP;
  UUID uses Node's cryptographic random source. Speed measurements use the
  existing transfer APIs; only the missing browser measurement was added.
- Projection: `npm run tools:catalog` generates the theme's `resources/tools.json`.
  `tools:catalog:check` fails a build if it drifts. PHP and React share this file.
  It is **presentation metadata, not a claim of runtime availability**.
- `/api/tools/navigation` (also `/api/v1/tools/navigation`) returns only ACTIVE,
  public, non-authenticated tools with actual handlers. Both global shells use
  it for menu/footer tool links. All Tools remains available without JavaScript;
  a failed availability request never inserts speculative individual links.

## Two native shells, one interface and execution service

**Node platform:** existing Layout/Header/Footer wrap the Tools landing, nine
category routes and tool pages. Search is name/description/slug/keyword based.
Unavailable entries are hidden initially and may be deliberately revealed with
their reason. Popular uses recorded executions from the existing 14-day query;
without records the UI explicitly labels its list “Selected essentials”. Recent
browser storage contains at most eight slugs, not inputs/results.

**WHMCS:** `tools/index.php` initializes the real `WHMCS\ClientArea`, resolves only
registered paths with `ToolsSite`, and uses the existing theme/header/footer,
Builder precedence and SEO hook. `cloudhost247-tools.tpl` mounts the **same** React
pages through `tools-embed.tsx`, without a duplicate header, iframe or business
logic. A missing bundle or platform mount returns an honest 503; unknown paths
return 404/noindex. Native PHP/global navigation still works when JS is disabled.

WHMCS sessions and Node JWT identities are deliberately **not interchangeable**.
The embedded API wrapper does not read/forward Node tokens. Authenticated,
owned-domain and account-portal operations remain on the platform. The handoff
uses the configured same-origin platform mount. No service credential is shipped
to JavaScript. Do not “solve” this separation by exposing an admin API token.

Builder-authored header/footer HTML still takes precedence, as before this
change. Installations using custom Builder shell overrides must include the
shared Tools navigation/footer component or update their override before launch;
this change does not silently replace administrator-authored layouts.

## Build and install

Build with the repository's supported Node CI versions (22.12+ or 24.8+):

```sh
cd cloudhost247-node
npm ci
npm run tools:catalog:check
npm run typecheck
npx tsc -p frontend/tsconfig.json --noEmit
npm test
# Choose the browser-facing mount for the platform build:
VITE_BASE_PATH=/platform/ npm run build
```

For a standalone root-mounted Node installation, omit `VITE_BASE_PATH` (default
`/`). The platform Router, API requests and static asset references honor the
build base. `APP_URL` must be the corresponding public HTTPS URL, including the
mount, for server canonicals. Never use a preview/localhost URL in production.

Artifacts:

| Artifact | Install location | Generated by |
|---|---|---|
| `cloudhost247-node/dist`, `public` | Node app deployment | `npm run build` |
| `assets/cloudhost247-tools/tools.js`, `tools.css` | WHMCS web root's `assets/cloudhost247-tools/` | `npm run build:tools` |
| `tools/index.php`, `tools/.htaccess` | WHMCS web root's `tools/` | source |
| `templates/cloudhost247/cloudhost247-tools.tpl` | matching active child theme | source |
| theme `lib/ToolsSite.php`, `lib/Site.php`, `resources/tools.json`, shared nav/footer/JS/CSS | matching WHMCS theme/module revision | source/projection |

Generated bundles are ignored by Git, not omitted from deployment. The cPanel
packager emits a separately named WHMCS Tools overlay alongside the Node ZIP.
Deploy the matching theme/module Git revision too; the overlay alone does not
upgrade an older theme. Never discard committed vendor `dist`/`out` runtime files
when packaging the **full** repository. The PHP release gate builds the Tools
adapter before checking asset references; build dependencies must be installed.

Set the existing theme admin `platform_base_path` to `/platform` (or the actual
same-origin mount). Proxy that mount to Node **stripping the mount prefix**.
Example nginx topology (adapt socket, PHP handler, WHMCS web root and limits to
hosting; this is not a complete WHMCS vhost):

```nginx
location /platform/ {
    proxy_pass http://127.0.0.1:3000/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    # At the trusted public edge overwrite, rather than trust, client-supplied IP headers.
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 70s;
    client_max_body_size 8m;
    client_body_timeout 15s;
}
# Route ONLY this public prefix to the PHP adapter. Deny directory listing/source files.
location = /tools { rewrite ^ /tools/index.php last; }
location /tools/ { rewrite ^ /tools/index.php last; }
# The existing secure PHP location must take /tools/index.php, preserving REQUEST_URI.
```

Apache deployments may use the scoped `tools/.htaccess` supplied here, requiring
rewrite support and permitted overrides. Do not replace WHMCS's root rewrite
rules. `/tools` must reach PHP, not expose the repository's developer scripts.
For subdirectory WHMCS installations, preserve the prefix in the PHP script name
and request URI; the adapter supplies it as Router basename. Validate this on
the actual web server. No browser code may point at `localhost` or another port.

Keep Node reachable only behind the configured trusted edge; otherwise spoofed
forwarded headers can defeat IP-based controls. Configure provider credentials
only through existing secure admin flows, install/migrate the Node database and
run the existing worker for provider/resolver/monitor health updates.

## Compatibility, metadata and limitations

Canonical pages are `/tools/{slug}`, with documented exceptions for What Is My
IP, IP-to-domain and ASN lookup. Registered old nested URLs redirect 301 on Node
and PHP and replace-history in React. API prefixes, internal IDs, old PHP addon
URLs, reports, favorites, history and MRZ consumers remain unchanged. Dynamic
`/domains/:domain/health` remains its original platform page; the new canonical
Tools route uses the same runner with the original ownership/auth gates. Embedded
visitors receive a valid platform sign-in handoff, not an unmounted SPA route.

Node serves tool-specific title, description, canonical and Open Graph metadata
before JavaScript. PHP uses the existing shared WebPage schema/metadata pipeline;
React updates metadata on client navigation. Unknown tools/categories get server
404/noindex. Interactive inputs/results require JavaScript and are not pre-run or
published for crawlers. No ratings, aggregate usage claims or fake FAQ answers
are inserted into schema.

Deployment acceptance still requires licensed WHMCS (hooks/session/sidebar/
Builder overrides), the hosting web server's rewrite/proxy, real credentials,
outbound DNS/TLS/RDAP and worker verification. Local PGlite + Smarty fixtures
are intentionally not presented as proof of those production behaviors.
