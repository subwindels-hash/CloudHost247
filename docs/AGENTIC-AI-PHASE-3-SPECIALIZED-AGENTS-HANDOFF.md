# Phase 3 — Specialized AI agents: local work in progress

**Status: IN PROGRESS / gate not met.** Phase 3 work was started at the user's direction while the Phase 2 gate remains incomplete; this does not approve or complete Phase 2, authorize deployment, or waive its orchestration, recovery and independent-review requirements. See `AGENTIC-AI-PHASE-2-ORCHESTRATION-HANDOFF.md`.

## First increment: knowledge audience boundary

The existing AI-OS knowledge source schema has no customer/public audience classification. It admits active runbooks, procedures, policies and other internal documents into the same search used by the account assistant. Therefore a customer question could receive an internal chunk, not merely a missing citation. Source type or an active status is not proof that content is public.

As a conservative interim change, the AI-OS `search_knowledge` tool is not customer-usable; the customer assistant catalog no longer grants it or `ai.knowledge.read`. The executor's customer gate blocks even an outdated grant, and the implementation rejects a direct call that carries a customer scope. The customer assistant's general-question fallback no longer performs this search and instead explicitly says search is unavailable and offers the existing support-ticket route. Staff knowledge search and the staff knowledge agent remain available. This is a deliberate reduction in customer functionality, not a completed customer knowledge specialist.

These controls are local code changes, not deployed security remediation. Old binaries can still expose unclassified knowledge, and previously persisted results or already-published messages are not scrubbed. Operators need a separately authorized incident/exposure and retention assessment before any deployment. The internal tool's direct-call safeguard depends on a trusted caller supplying customer scope; it is not authentication, and unscoped internal APIs must not be exposed as customer entry points. Other knowledge systems, including the public AI website retrieval pipeline, are separate surfaces and are not certified by this change. No claim is made that all private data flows or derived outputs are safe.

## Customer activity disclosure boundary

A customer attribution on an AI task, finding or approval is not proof that its text is customer-safe. The previous customer activity path returned staff task summaries, findings and approval actions solely on that attribution; it could also return historical customer task summaries created before the knowledge-search restriction. The customer-scoped activity tool now returns only ID, status and timestamps for a bounded list of customer-initiated `customer.assistant_query` tasks belonging to that same user and the customer assistant agent. It excludes all summaries, results, contexts, staff/workflow tasks, findings and approval details. For compatibility the latter two arrays are empty; `visibility: recent_customer_assistant_tasks_only` explicitly means they are not included, **not** that none exist. The customer profile no longer exposes the count of all customer-attributed AI tasks. Staff-scoped activity retains its existing broader view.

The customer assistant now has the appropriate scoped activity-tool grant and reports only a limited request list, and the UI no longer claims a complete activity register or presents an unavailable response as zero. The API is a capped snapshot (account UI 25, assistant 20; tool max 100), not a complete audit, customer-notification mechanism or evidence that an action succeeded. Query cost is not guaranteed bounded by the output limit. This intentionally reduces customer transparency pending an explicit, independently reviewed publication model. Existing stored data and earlier disclosures are unchanged; old application binaries remain unsafe for this boundary. The direct-tool scope is trusted server context, not authentication. The change does not certify other customer-facing surfaces or protect against arbitrary unsafe future handlers.

## Customer domain and certificate expiry answers

The customer assistant's domain and SSL responses now describe the actual filtered local-record query instead of asserting that no domain expires or no certificate has failed when the query returned no rows. It shows up to 10 of at most 100 records with known expiry before the 90-day cutoff (including past dates), states that other statuses and unknown expiry are excluded, and explicitly disclaims a complete inventory and live registrar/TLS verification. SSL failures beyond the cutoff, missing expiry and revoked certificates are not covered; domain pending-migration rows and unknown expiry are not covered. Domain answers explicitly state that DNS records cannot be inspected. Domain/certificate renewal questions take precedence over the generic subscription renewal route, and UI suggestions no longer imply a DNS lookup or full status check. This does not add a domain/SSL specialist, live integrations or complete lifecycle coverage; separate staff handlers and other surfaces have not been comprehensively audited for equivalent claims.
