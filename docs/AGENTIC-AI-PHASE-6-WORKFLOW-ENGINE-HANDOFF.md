# Phase 6 — Autonomous Workflow Engine: local work in progress

**Status: IN PROGRESS / gate not met.** Started at the user's direction; this does not waive the incomplete Phase 2–5 gates or authorize staging, deployment, provider calls or new autonomous writes. The separately named historical commerce/billing Phase 6 is not the scope of this handoff.

## Existing foundation and new increment

The event dispatcher already uses non-expiring, token-checked event claims, prepares tasks and checkpoints dispatch in one transaction, stops on incomplete outcomes and holds claims instead of replaying uncertain actions. Phase 2's handoff describes the design and existing limitations. It is not an end-to-end fenced engine or a recovery system.

The dispatcher previously trusted a returned successful task object/status without re-reading the durable task after execution. A stale or inconsistent result could therefore advance a workflow even if the database task was still queued, changed identity, or had an approval record. This increment adds a transaction for successful fresh **and reused** tasks: lock the event claim, lock and re-read the task, check its persisted success and prepared routing/scope/context/idempotency identity, require no associated approval records, and write the success checkpoint before releasing those locks. Otherwise the step becomes `outcome_unknown`, subsequent steps do not run, and the event remains claimed for investigation. A failed/lost checkpoint commit response is also treated as uncertain and does not authorize replay. This deliberately rejects even previously executed or rejected approval records on a purportedly successful task; some historical or inconsistent work may remain held.

This check establishes only a database observation. A succeeded task can still represent an incorrect result; no upstream effect, payment, provisioning or verification is proved by task status. The claim and task locks do not fence external effects, prevent changes after commit, serialize every approval creation or agent/grant revocation with future dispatch, or make later workflow completion and event acknowledgement one atomic transaction. A claim may remain held indefinitely, including after an uncertain commit. No recovery, replay, cancellation or automatic approval-resume behavior has been added. The approval-existence check has no new index: result bounds do not bound query work, and production volume, locking and rollout compatibility require review. No migration or public API change was made.

## Follow-up: per-workflow preflight

The dispatcher now validates and resolves the entire individual workflow before dispatching its first step. Definitions are strict and limited to 1–20 unique agent slugs with recognized fields, bounded names, priorities, 32 top-level input keys and 32 KiB per resolved input. Whole-value `{{key}}` placeholders require an own, non-null event payload property; scope and subject references require UUIDs. Partial/nested template syntax and invalid/special top-level keys are rejected rather than silently interpreted or dropped. Missing or malformed later-step values fail the workflow with a generic error and leave the claim held; they no longer silently become a null customer/subject or an omitted input after an earlier step has run. This may block historical/custom definitions that relied on permissive or optional values. The seeded definitions passed the focused regressions.

At the time of this increment validation was per workflow only; the later event-wide captured-set preflight is documented in the Phase 2 handoff. A later workflow may still fail after earlier effects for reasons not covered by that syntactic preflight. Payload values are still untrusted data; syntactically valid UUIDs do not establish ownership, event authenticity, actor authority, or per-task input semantics. Nested arbitrary data, denial-of-service limits before database retrieval, side-effect authorization, template meaning, definition/version changes and seeded auto-updates require further review. Claims are not automatically released or replayed. No migration, public API, live effect or provider call was added.
