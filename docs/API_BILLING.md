# Billing API Contract (Phase 5B)

This document is the API contract for Phase 5B, "Billing foundation": real invoices, issued
automatically and atomically when an order is checked out (Phase 5A), and the append-only billing
ledger behind them. Keep this in sync with the code — the source of truth is
`cloudhost247-node/src/routes/billing.ts`, `cloudhost247-node/src/services/billing-service.ts`, and
`cloudhost247-node/database/migrations/0018`–`0020`; this document should never describe behavior
the code doesn't actually have.

See `docs/API_COMMERCE.md` for the cart/order layer this builds directly on top of.

## Explicit non-goals (this phase)

- **No payment gateway, no way to create or mutate a payment, and no way for any invoice to become
  `paid`.** `database/migrations/0020_create_payments.sql` adds the `payments` table schema and
  `src/db/payments.ts` adds its repository functions, but **no route or service anywhere calls
  them** — grepping every route file for `createPayment` is one of the tests in
  `tests/integration/billing-schema.test.ts`. This is deliberate groundwork for Phase 5C (the
  gateway abstraction, a manual/offline gateway, and a self-contained sandbox gateway with
  simulated signed webhooks), not a working payment flow. Every invoice this phase creates starts
  and stays `status: 'unpaid'`.
- **No tax or discount configuration system yet.** Exactly like `orders` (Phase 5A), an invoice's
  `discount_amount`/`tax_amount` are always `"0.00"` — a genuine zero, copied verbatim from the
  order, never fabricated.
- **No admin/staff invoice-viewing routes yet.** Deferred to Phase 5F, same as Phase 5A's
  order-viewing routes.
- **No customer billing UI wiring yet** (the `/billing`/`/invoices` frontend pages) — that's Phase
  5E. This phase is backend-only, per the locked "checkpoint after every sub-phase" cadence.
- Still single-currency (`USD`), still no cPanel/WHM/registrar automation of any kind.

## Architecture

```
Billing API (Fastify routes)
  src/routes/billing.ts         (/api/v1/invoices*)
        │
        ▼
Service layer
  src/services/billing-service.ts
    issueInvoiceForOrder()  <───── called only from inside
                                    src/services/commerce-service.ts#checkoutCart's
                                    single withTransaction call (see below)
    listMyInvoices() / getMyInvoiceDetail()
        │
        ▼
Repository layer
  src/db/invoices.ts        src/db/billing-ledger.ts       src/db/payments.ts
  (invoices)                (billing_ledger, append-only)  (schema-only in 5B — see above)
        │
        ▼
PostgreSQL (database/migrations/0018..0020), joined through the Phase 5A order/order_items tables
```

Every response is built only through `src/dto/billing.ts` — the same "never leak an internal field,
never fabricate a value" mapping-layer pattern used throughout this codebase.

## Data model summary

- `invoices` (`0018`) — the formal billing document for an order. **One invoice per order** in
  this phase (`order_id` is `UNIQUE`) — there is no recurring/subscription billing yet.
  `invoice_number` is generated by the database itself from a dedicated `invoice_number_seq`
  sequence (`'INV-' || lpad(nextval(...)::text, 8, '0')`), the same proven, race-free pattern as
  `orders.order_number` (Phase 5A) — never client- or app-supplied.
  `subtotal_amount`/`discount_amount`/`tax_amount`/`total_amount`/`currency` are a **snapshot**
  copied from the order at the moment the invoice is issued, not a live join — an invoice is its
  own billing record. `due_date` defaults to the issue date (due on receipt) — there is no
  payment-terms configuration system yet, and this migration does not invent one. `status` starts
  at `unpaid`; its full lifecycle (`unpaid` / `paid` / `void` / `refunded` / `partially_refunded`)
  exists in the schema now so Phase 5D's verified-webhook processing can use it later, but no code
  in this phase ever sets it to anything else. `order_id`/`user_id` are both `ON DELETE RESTRICT` —
  a customer or order with an invoice can never be deleted out from under it.
- `billing_ledger` (`0019`) — the append-only, immutable financial audit trail the Phase 5 spec
  calls for explicitly. Every row is one financial fact: `charge` (an invoice was issued — the
  only entry type any code creates as of Phase 5B), `payment`, `refund`, or `credit` (all reserved
  for later phases). `amount` is always a positive magnitude; the accounting direction is implied
  entirely by `entry_type`. **This table is enforced insert-only at the database level, not just by
  application discipline**: `BEFORE UPDATE`/`BEFORE DELETE` triggers make any mutation attempt fail
  outright — including from a future bug, a manual `psql` session, or a compromised admin route —
  proven directly in `tests/integration/billing-schema.test.ts` (a raw SQL `UPDATE`/`DELETE`
  against the table, and the same attempted inside a transaction, both rejected with the row
  unchanged). Correcting a mistake always means inserting a new, reversing entry — never editing or
  removing the original.
- `payments` (`0020`) — schema only as of this phase (see "Explicit non-goals" above). Models the
  real payment lifecycle the Phase 5 spec calls for (`pending` / `successful` / `failed` /
  `cancelled` / `expired` / `refunded` / `partially_refunded`). A partial unique index on
  `(provider, provider_reference)` (enforced only when both are present) is already in place —
  the exact idempotency guarantee Phase 5D's webhook handling will depend on, so the same verified
  webhook event replayed twice can never create two payment records.

## Checkout now issues a real invoice atomically (extends Phase 5A)

`checkoutCart` (`src/services/commerce-service.ts`) now also calls
`issueInvoiceForOrder` (`src/services/billing-service.ts`) **inside the same `withTransaction` call**
as the order/order_items insert and the cart clear. The order, its items, its invoice, and that
invoice's opening `charge` ledger entry are one atomic unit — a checkout can never produce any
strict subset of the four (proven by the existing Phase 5A "reject an empty/unavailable cart, zero
orders created" tests, which now also implicitly prove zero invoices/ledger entries are created).
`POST /api/v1/orders`'s response now includes `invoiceId`/`invoiceNumber` directly on the order, and
`GET /api/v1/orders` / `GET /api/v1/orders/:id` include the same fields for every existing order.

## Authorization model

Identical pattern to Phase 5A/4: `authenticate()` on every request, every query scoped to the
caller's own `user_id`. An invoice that exists but belongs to a different customer is never
distinguishable from one that doesn't exist — both `404`, never `403`.

| Capability | customer | admin | super_admin |
|---|---|---|---|
| View own invoices/ledger detail | ✅ (self only) | ✅ (self only) | ✅ (self only) |
| Create, edit, or void any invoice | ❌ | ❌ (deferred to 5F) | ❌ (deferred to 5F) |
| View another customer's invoice | ❌ | ❌ (deferred to 5F) | ❌ (deferred to 5F) |

There is no `POST`/`PATCH`/`DELETE` route for invoices anywhere — an invoice is only ever produced
as a side effect of checkout, never directly created or edited by any request.

## Endpoints

All endpoints require `Authorization: Bearer <token>` and return `401` if missing/invalid.

### `GET /api/v1/invoices`

Lists the caller's own invoices (summaries), newest first.

```json
{
  "invoices": [
    {
      "id": "…", "invoiceNumber": "INV-00000001",
      "orderId": "…", "orderNumber": "CH-00000001",
      "status": "unpaid", "currency": "USD",
      "subtotalAmount": "24.50", "discountAmount": "0.00", "taxAmount": "0.00", "totalAmount": "24.50",
      "dueDate": "2026-09-28", "issuedAt": "2026-09-28T…"
    }
  ]
}
```

### `GET /api/v1/invoices/:id`

Full invoice detail: the invoice fields above, plus `items` (the underlying order's line-item
snapshots — see `docs/API_COMMERCE.md`) and `ledger` (every `billing_ledger` entry recorded against
this invoice, oldest first). Ownership-checked (`404`, not `403`, for another customer's invoice).

```json
{
  "invoice": {
    "id": "…", "invoiceNumber": "INV-00000001", "orderId": "…", "orderNumber": "CH-00000001",
    "status": "unpaid", "currency": "USD",
    "subtotalAmount": "24.50", "discountAmount": "0.00", "taxAmount": "0.00", "totalAmount": "24.50",
    "dueDate": "2026-09-28", "issuedAt": "2026-09-28T…",
    "items": [
      { "id": "…", "productName": "Hosting", "planName": "Starter", "billingPeriod": "monthly",
        "quantity": 1, "unitPriceAmount": "24.50", "lineTotalAmount": "24.50", "currency": "USD" }
    ],
    "ledger": [
      { "id": "…", "entryType": "charge", "amount": "24.50", "currency": "USD",
        "description": "Invoice INV-00000001 for order CH-00000001", "createdAt": "2026-09-28T…" }
    ]
  }
}
```

## What's next (later Phase 5 sub-phases)

- **5C** — the payment gateway abstraction, a fully-featured manual/offline gateway, and a
  self-contained sandbox gateway with simulated signed webhooks; checkout initiation actually
  starts populating the `payments` table this phase left ready but unused.
- **5D** — signature-verified, idempotent, replay-protected webhooks — the *only* way an invoice's
  `status` or an order's `payment_status` can ever become `paid`.
- **5E/5F** — customer-facing billing UI (`/billing`, `/invoices`) and admin/staff billing
  management + audit trail.
- **5G** — SMTP notifications (order confirmation, invoice, payment) and reconciliation jobs.
