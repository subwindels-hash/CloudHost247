# Agentic AI — Phase 2 orchestration foundation: developer handoff

**Status: IN PROGRESS / gate not met.** This includes a narrow, locally tested read-only website-launch state machine and shared internal task preparation integrated with the existing AI-OS executor, not the fully authorized, durable central orchestrator requested for the complete platform. It does not certify Phase 2 or authorize staging, deployment, billing changes, or live provider calls. Phase 3 work has started at the user’s direction without waiving the Phase 2 gate. Phase numbering follows the user's ten-phase sequence.

## What was implemented

- `cloudhost247-node/src/ai-os/runtime/customer-orchestrator.ts` — a bounded internal, strictly validated intent contract shared by the existing account assistant and website-launch entry points. It fixes operation-to-agent/task mapping in server code, validates active named actors and conversation consistency, and delegates to existing AI-OS task and tool gates. It is not an authentication boundary and does not accept arbitrary agents, tools, or client-chosen scope. Routes must authenticate or validate visitor access first. The account assistant retains its existing capabilities, including creation of a local support ticket on an explicit request; only the website-launch lookup is read-only. Staff, event/workflow and board dispatch retain their separate entry-point contracts.
- `cloudhost247-node/src/ai-os/workflows/launch-orchestrator.ts` — server-side, conversation-scoped state for a specific launch intake: `awaiting_choice`, `checking`, `options_ready`, `needs_support`, `cancelled`, `escalated`. A partial unique index limits the conversation to one active request. A conditional update claims a choice once; state transitions and their minimal audit entry share a transaction. `checking` is deliberately not automatically replayed after interruption.
- `cloudhost247-node/database/migrations/0109_ai_launch_orchestration.sql` — local schema for that state, a conversation reference and optional link to the existing `ai_tasks` row. Stores no transcript or provider payload. **Not applied to staging or production**; any deployment requires separate authorization and must also address prior migration `0108`.
- `cloudhost247-node/src/services/ai-website-launch.ts` — uses the workflow ID as the task idempotency key and creates and attaches the new task in a single transaction before dispatch. The link checks the task's conversation, type, service and idempotency key. Execution delegates to the existing registered, permission-limited read-only AI-OS task and WHMCS orderability tool. No checkout, write, payment or provisioning is initiated. Existing task grants, auditing, validated outputs, failure handling and no-fabricated-price policy still apply.
- `cloudhost247-node/src/routes/ai-support.ts` — existing ownership/token check precedes access; current conversation and workflow identifiers are derived on the server, not accepted as arbitrary client task scope. A visitor token accompanied by an unrelated authenticated account cannot attribute the task to that account. Existing support/security guardrails take precedence. The existing conversation GET optionally returns `{status, label, attentionRequired}` as `launchProgress` when the flag is enabled; other visitors cannot read it. Exact cancellation phrases stop the active state; escalation stops it for handoff. The lookup's terminal transition, its transition audit and its transcript message commit together, with the conversation row locked and checked for `AI_ACTIVE`. A stop that wins first suppresses publication; if publication wins first it commits before the stop. New admin-only `POST /api/v1/admin/ai-support/conversations/:id/launch-workflows/:workflowId/reconcile` accepts only explicit `{confirmed:true, disposition:'needs_support'}` and returns conflict for stale, nonchecking or not-yet-delayed requests; no provider call, task replay or customer account write occurs. Transition and minimal fixed-reason AI audit commit together.
- `cloudhost247-node/frontend/src/components/AiSupportWidget.tsx` — displays progress on transcript refresh. A checking state unchanged for five minutes is labeled as potentially interrupted, without asserting failure or changing state. The feature remains behind the pre-existing default-off `AI_WEBSITE_LAUNCH_ENABLED` flag.
- `cloudhost247-node/frontend/src/pages/AdminAiSupportPage.tsx` — staff support conversation detail displays minimal workflow ID, status, warning and linked task ID/status from the existing role-gated admin endpoint. Opening a different conversation clears old detail and ignores stale detail responses. Admins/super-admins can explicitly mark a delayed lookup as needing support after a confirmation; the server also enforces a five-minute delay and checks the exact conversation and workflow. This fences later answer publication but neither retries the task nor cancels an upstream lookup.
- `cloudhost247-node/tests/integration/ai-website-launch.test.ts`, `tests/integration/migrate.test.ts` — expanded local verification and migration inventory.

The support and account-assistant experiences share the bounded dispatch contract but their conversations and product experiences are not unified. The shared contract currently has only two fixed customer operations, not general staff/event orchestration, an arbitrary tool runner, distributed workflow engine, or customer memory store. Existing AI-OS run, task, step and audit records remain authoritative for execution; the additional launch row records only conversational orchestration state.

## Shared task preparation and workflow checkpointing

- `runtime/task-orchestrator.ts` is now used for internal task creation by the customer dispatcher, staff tasks and copilot, event workflows, scheduled scans, board briefings and child agents. It compares the complete persisted task identity, including JSONB input and actor/customer scope, before returning a duplicate idempotency key; a mismatch fails closed without revealing the old task. This is shared preparation, **not** a central authorization boundary, durable dispatcher, task lease, or guarantee of exactly-once execution. Existing callers remain responsible for deriving and authorizing their scopes; existing executor grants and approvals remain in force.
- Workflow dispatch locks and verifies the event claim, prepares the task and writes its `dispatching` checkpoint in one database transaction before invoking the runner; it records observed outcomes before progressing. A failed transaction, changed task identity, or lost COMMIT acknowledgement leaves the claim held and the workflow run `running` for investigation; the runner is not invoked. A lost acknowledgement can nevertheless mean the task and checkpoint committed, so it must not be treated as proof of rollback or permission to retry. This requires a transaction-capable pool/PGlite handle, not a bare query-only handle. A reused success cannot advance a workflow after the agent or its declared task grant is disabled. Repeated agents in a single workflow remain rejected because the historical idempotency key is keyed by agent slug, not step position. A process may still disappear between later statements; a running row is not proof of either an effect or a safe retry.
- The executor now validates persisted actor/customer scope and customer active status **before** it claims a task or returns a previously claimed/completed task. A supplied actor must match the persisted requester; supplied customer scope must match a consistent customer task, and non-customer tasks reject a supplied customer scope. A rejected check records a minimal denial audit and throws a generic error without returning task contents or changing the queued task. The queued-to-running update also compares the checked agent, task type, requester/type and customer ID and checks that a customer is active in that statement; on an unsuccessful claim it rechecks scope and identity before returning an existing state. Malformed or suspended customer tasks remain queued and need investigation. This is a consistency guard, **not** authentication or full authorization: omitted identity options remain allowed for trusted internal callers, and a non-customer task's `customer_id` is not an end-user security boundary. Entry points must authenticate, derive scope and reauthorize independently.
- The original active-customer predicate used only a statement snapshot; later follow-ups below add customer and certain staff role row locks through claim, not through the subsequent handler. Other staff paths and agent grants are not all rechecked atomically by claim. No check can cancel an effect already dispatched. Further coordinated authorization and effect fencing remain necessary. A denied caller can no longer mark a valid queued task failed, and retries of suspended or malformed tasks are not automatic.
- Board and child-agent duplicate tasks are not automatically replayed, including queued tasks; a board task whose grant is revoked cannot produce a new report from a cached success. Scheduled scans likewise do not restart existing queued tasks. This safety tradeoff can leave queued work needing investigation. The board child-key collision this caused across actors is addressed in the cross-actor key scoping follow-up below. No automatic recovery is added.

## Non-expiring event claims (local only)

- Migration `0110_ai_event_dispatch_claim.sql` adds a random internal owner token and claim timestamp. The dispatcher atomically claims one unprocessed event at a time with `FOR UPDATE SKIP LOCKED`; a concurrent worker cannot normally claim it. Workflow run creation, checkpoint and completion and event acknowledgement require the matching token. Claim timestamps are visible via the existing permission-gated events view; tokens are excluded from event API responses. The `dispatched` counter counts workflows whose dispatcher returned, not proof that no effect occurred when it is zero.
- Claims have **no timeout, automatic takeover, release or resume**. A worker death or persistence failure leaves the event claimed and unprocessed, even if its effect already happened. Any incomplete workflow now retains the claim and stops later workflows for that event, including `failed`, `cancelled`, `awaiting_approval`, `outcome_unknown`, `queued` and `running` steps, or invalid definitions and missing agents. Inconsistent task/run identities, statuses or approval state and unrecognized runner statuses are treated as `outcome_unknown`. Only an event with all selected workflows observed successful (or none selected) is acknowledged. The `dispatched` counter still counts a finished workflow attempt, not an external outcome. An operator can record attention for an old claim as described below, but this does not resolve it. Investigate associated runs/tasks/audits; elapsed time alone is not proof the worker died or the effect failed. Do not clear the claim, replay the event, or treat a missing acknowledgement as evidence of failure. For new workflows, task preparation and pre-dispatch checkpoint commit together, but older records and other task paths may still lack run-step references.
- This is an intentional **availability tradeoff**: approval pauses, missing agents and invalid workflow definitions can now strand events indefinitely, even after configuration is fixed or an approval is decided. Approval execution remains a separate existing action: it can execute an approved tool while the event remains held; holding the claim does not cancel or fence that action. A later task status change does not resume the workflow or release the event. There is no supported operator resolution path. Previously acknowledged incomplete events are not retroactively re-claimed or displayed in the held queue. Successful status is not independently verified provider outcome or end-to-end exactly-once evidence; an evidence-based reconciliation model and review of all effect and approval boundaries are still required before production.
- Matching-token database checks are **not end-to-end side-effect fencing**: they cannot recall a dispatched tool or guarantee an external system checks the token. Manually changing a token while a worker is active could race with a dispatch. There is no heartbeat, operator resolution workflow, external-effect fencing, outbox, end-to-end exactly-once guarantee, or multi-node crash certification. Existing event fingerprint deduplication also remains non-atomic.
- The migration quarantines legacy unprocessed events with any recorded workflow run by assigning a non-expiring claim; events without runs remain available. **Not deployed.** A separately authorized rollout must stop all old event processors before migration and prohibit mixed old/new binaries: old code ignores claims and could replay an event or expose token columns. Do not roll back to old workers against these claims; an independently reviewed quiescence, recovery and rollback procedure is still required. Claiming events changes availability: quarantined and crashed events intentionally need human investigation and currently have no in-product resolution path.

## Held-event investigation records (local only)

- Migration `0111_ai_event_investigations.sql` stores an event ID, the exact database claim timestamp, operator and creation time. It stores no claim token, event payload, free text or provider outcome. A unique constraint limits records to one per observed event claim. Its foreign key **restricts deletion of an event with a record**; retention, privacy/deletion handling and an approved archival procedure must be designed before deployment. The migration is not deployed.
- `GET /api/v1/admin/ai/event-claims` requires `ai.events.view` and returns at most 200 oldest currently held claims, excluding claim tokens and event payloads. `POST /api/v1/admin/ai/events/:id/investigations` requires `ai.workflows.manage` (admin/super-admin), a strict `{confirmed:true}` body, and a still-held claim at least five minutes old. The server rechecks and locks the operator's active role and the event row inside a transaction; creation and the fixed, minimal AI audit record commit together. Concurrent submissions return the same record without duplicating the audit. The cutoff is only an age heuristic and does not prove a worker has stopped.
- The AI Command Center's Events & Workflows tab shows up to 100 oldest held claims and, on request, up to 50 filtered workflow-run references for an event. It now renders the actual `occurred_at` field rather than an incorrect `emitted_at` field. The control is confirmation-gated and makes clear that **recording is not cancellation, replay, assignment, notification, resolution or verification**. A no-run result does not prove no work occurred. After the real owner acknowledges an event it disappears from the held queue, while its claim investigation record and audit remain; the acknowledged-run panel described below can record a separate investigation for an incomplete run but cannot display historical claim investigation records. There is no case closure or retention mechanism. UI tests are DOM simulations, not browser accessibility or E2E certification.
- A recorded investigation cannot fence an in-flight effect or release a claim; it cannot be treated as recovery completed. Manually resetting a claim or processing an uncertain event remains unsafe. The UI and API do not contact a provider or create a support ticket, page an operator, or establish who is responsible. Full evidence-based reconciliation and independently verified operational procedures remain Phase 2 gaps.

## Acknowledged incomplete workflow visibility (local only)

- `GET /api/v1/admin/ai/acknowledged-incomplete-workflows` requires `ai.events.view` (currently admin/super-admin) and returns up to 200 recent `running`, `partial` or `failed` workflow runs whose still-existing event has a non-null `processed_at`. The default and UI limit are 100. It exposes run/event IDs, event type, workflow slug, status, timestamps, a microsecond-precise acknowledgement key and minimal current investigation metadata, not stored steps, errors, payload, task context or claim token. Authorization uses the database-rechecked role. The read does not re-claim, mutate, notify, verify or create an investigation record.
- The new separate command-center panel shows these limited references, maintains an independent error state and discards stale refresh responses. It is not a resolution list: a run may already have been investigated, a running status may be active or stale, and an acknowledgement does not establish an external outcome. It omits older entries beyond the limit, successful runs, deleted events and deleted workflow runs, and events with no run. There is no pagination, historical claim reconstruction or case closure. An empty result is not evidence that no action needs review. Use authorized workflow/task/audit records and independently established operational procedures for investigation; never replay solely because a run appears here.
- `POST /api/v1/admin/ai/workflow-runs/:id/acknowledged-investigations` records operator attention only, with strict confirmation, the displayed event ID, exact UTC microsecond acknowledgement key and displayed run status. It requires `ai.workflows.manage`; the transaction rechecks and locks the active operator role, then the event and run, and refuses a stale association, acknowledgement or status. It stores the exact database timestamp and status, and commits a minimal fixed audit entry atomically; parallel submissions for the same run/event/acknowledgement return the same record. Existing attention does not establish whether work happened, and does not cancel, retry, assign, notify, resolve or verify anything. The run can continue or change status after the record is created; the panel displays the status observed when attention was recorded. A record can disappear from this limited panel if the run later succeeds or leaves the top 100; no history/closure UI exists for those records. Timestamp identity cannot distinguish a manually recreated acknowledgement with the exact same timestamp; no manual claim reset or re-acknowledgement is supported. Lost transaction COMMIT acknowledgement can leave the response uncertain; refresh rather than assuming rollback.
- Migration `0113_ai_acknowledged_run_investigations.sql` is **not deployed**. Its `ON DELETE RESTRICT` references to both event and workflow run also prevent deleting the associated workflow via its cascading run relationship, and may affect retention and privacy deletion. An approved retention/deletion/archival policy is required before deployment. The new list endpoint also requires this migration; deployment ordering must be reviewed. No free text, event payload, tool arguments or provider outcome is stored.
- New migration `0112_ai_incomplete_workflow_runs_index.sql` creates a partial recent-run index to support this query. **Not deployed**. A result limit does not guarantee bounded database work: joins may still scan many rows. The index is built by ordinary transactional `CREATE INDEX` and can block writes on a large table; rollout requires independent query-plan/load review and an approved migration window or separately reviewed operational migration strategy. It does not create historical data or change retention/deletion behaviour.

## Security and operational boundaries

- Route ownership is mandatory; the orchestration module is an internal helper and **does not itself authorize callers**. Other integrations must independently establish server-derived scope before calling it.
- Intake, AI answer and escalation publication, cancel and reconcile transitions all take the conversation row lock and verify fresh status; a takeover or closure that wins first suppresses later AI publication, and an attached queued lookup task is cancelled in the same transaction as the stop (an already-claimed run continues and can only publish while the workflow state still permits it). Attachment only commits from `awaiting_choice` under the same lock, so it cannot land after a stop that already won. These paths do not cover dispatch, the upstream call, the HTTP reply or external effects; escalation does not cancel an attached queued lookup (its publication is fenced by workflow state), and cancellation cannot recall a read-only lookup already dispatched. Do not apply this design to write actions without stronger fencing and end-to-end atomicity.
- A `checking` row unchanged for five minutes is displayed as potentially interrupted; this is an age heuristic, not proof of failure, not a timeout and not a lease. An administrator can fence that one delayed read-only workflow and mark it `needs_support` after explicit confirmation. The associated task may still be running or finish; neither provider cancellation nor verified outcome is implied. This does not reconcile arbitrary tasks or approval executions. There is no recovery worker, event outbox, automatic retry, or distributed exactly-once guarantee.
- Actual human support handoff is managed by the existing support code, separately from the orchestration transition. `escalated` means stopped for handoff, not proof of agent assignment or ticket creation. The administrator's `needs_support` action does not create a ticket, notify the queue, or assign a person. If handoff fails it must be investigated. The recovery endpoint is unavailable when the launch flag is off; switching the flag off does not reconcile existing rows.
- Read-only mock results do not establish live WHMCS correctness or real-time pricing. Catalogue data may be cached; the checked-in service mapping remains unbound. The flow does not verify order/payment/provisioning outcomes.
- The targeted real-PostgreSQL tests do not certify multi-node behavior, recovery after process termination at every boundary, browser accessibility, isolation under all auth combinations, full test-suite compatibility, staging, or production. No live integrations, production knowledge indexing, real customer account mutations, orders or payments were performed.

## Reproducing the optional local PostgreSQL tests

This is a **local test-only** procedure, not a deployment. It needs Node/npm and outbound npm registry access. Use a disposable checkout, and do not substitute any existing database, production socket, or `DATABASE_URL`. The package and cluster are written under ignored `.cache`; no dependency or lockfile is added to the application. The suite is skipped by default and independently verifies the server's exact data directory, Unix-only networking, database and user before applying migrations.

From the repository root, with no pre-existing `.cache/local-postgres/data`:

```sh
mkdir -p .cache/local-postgres/socket
chmod 700 .cache/local-postgres/socket
npm install --prefix .cache/local-postgres --no-audit --no-fund --ignore-scripts @embedded-postgres/linux-x64@18.7.0-beta.19
node .cache/local-postgres/node_modules/@embedded-postgres/linux-x64/scripts/hydrate-symlinks.js
export LD_LIBRARY_PATH="$PWD/.cache/local-postgres/node_modules/@embedded-postgres/linux-x64/native/lib"
export PG_BIN="$PWD/.cache/local-postgres/node_modules/@embedded-postgres/linux-x64/native/bin"
"$PG_BIN/initdb" -D "$PWD/.cache/local-postgres/data" --auth=trust --no-locale --encoding=UTF8 -U ai_local_test
"$PG_BIN/pg_ctl" -D "$PWD/.cache/local-postgres/data" -l "$PWD/.cache/local-postgres/log" -o "-k $PWD/.cache/local-postgres/socket -c listen_addresses='' -p 56432" -w start
(cd cloudhost247-node && RUN_ISOLATED_AI_POSTGRES_TESTS=1 npx vitest run tests/integration/ai-orchestrator-local-postgres.test.ts --maxWorkers=1)
"$PG_BIN/pg_ctl" -D "$PWD/.cache/local-postgres/data" -w stop
```

The private socket directory is mode 0700; `trust` is suitable only for this isolated local test. The cluster is disposable and never used as application preview or production storage.

## Approval decision and execution hardening (local only)

Human approval decisions now recheck and share-lock the active approver with the required permission, and commit the single-winner decision and platform audit in one transaction. A revocation that obtains the user-row lock first is observed; one after the decision commits is not prevented. If COMMIT acknowledgement is lost, the route does not execute the action and cannot infer rollback: a committed approved decision can remain unexecuted and requires operator investigation. No automatic recovery is introduced.

Approval execution rechecks that any customer-scoped account is active before invoking its tool. This is a snapshot, not a lock or revocation fence: suspension immediately after the check can still race with the effect. Denial or final approval status and the corresponding AI audit are now transactional. Tool effects and tool-call records are outside that transaction: an audit failure after a real effect leaves the approval `executing` and prevents automatic replay, but does not undo the effect or establish its outcome. These checks do not provide exactly-once effects or a complete reconciliation mechanism.

## Follow-up: event-wide definition preflight

For each claimed event the dispatcher now validates and resolves the captured list of enabled workflow definitions before dispatching the first workflow. If any definition or required event input is invalid, it records a generic failed run for the first invalid workflow where possible, leaves the claim held, and dispatches no tasks for that captured event. It does not expose rejected payload data in the failure. `dispatched` still counts that recorded failed workflow, not an executed task. If failure-record persistence fails, the claim remains held. This intentionally changes behavior for events that previously executed an earlier valid workflow before encountering a malformed later workflow; availability may decrease until definitions are fixed and claims manually investigated.

This is a syntactic preflight of a point-in-time captured list, not authentication or authorization of the event, customer ownership, per-task semantics, a lock on later workflow/grant changes, cross-workflow transactional execution or an external-effect fence. The subsequent registry admission preflight below checks agent existence and grants before dispatch and again per step; another failure or revocation can still occur after an earlier workflow has run. ## Follow-up: atomic event fingerprint deduplication (local only)

`emitEvent` previously checked a fingerprint with `SELECT` and then `INSERT` in separate statements; two concurrent emitters could both pass the check and insert duplicate events, each of which dispatches its own workflow executions (workflow idempotency keys are per-event, so duplicates are not collapsed). ## Safe-retry specification (local)

Safe by construction, already enforced, unchanged by this increment:

- Fingerprinted event re-emission inside the suppression window — atomically deduplicated; after the window a re-emission is a new event by design.
- `prepareOrchestratedTask` with an existing identical key — returns the existing row (a record read), never re-executes.
- Bucket-locked scheduled scans — a bucket already recorded never relaunches.
- A recorded workflow success checkpoint — advances the run as evidence of recorded state, not as a new execution.

Never auto-replay (prohibited; enforced by held claims, single-winner identity claims and status gates):

- `running`, `outcome_unknown`, `awaiting_approval` and `queued` tasks (a queued task may belong to a live worker), held event claims, approvals in `executing`, and launch rows in `checking`.
- Age or heartbeat staleness is never sufficient evidence to retry: the sweep only counts suspected interruptions and investigation endpoints only record attention.

Explicit operator retry of a read-only task — **implemented in the follow-up below** under exactly these rules: a dedicated permission (`ai.tasks.retry`, admin/super_admin only); re-verified persisted identity, agent grants and actor/customer scope; proof the task was never claimed (queued, no runs, no tool activity, scheduled time reached); a server-code whitelist of read-only task types (never client input); a mutating-tool refusal gate inside the run itself; and an audited decision before dispatch. It still cannot prove provider-side idempotency — external writes need provider idempotency keys before any write-path retry could be safe, which is why the whitelist contains only audited read-only types.

Ownership/fencing inventory (none is an end-to-end effect fence): event dispatch claim token (0110), approval execution claim (0108), single-winner task claim UPDATE with identity recheck, workflow checkpoint token, launch conversation row lock (0109), and the new heartbeat observations (detection only).
