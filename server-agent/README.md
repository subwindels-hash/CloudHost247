# CloudHost247 Server Agent

The CloudHost247 Server Agent is the only component that touches Docker on a customer VPS or
dedicated server. It runs as a small, dependency-free Node.js service (Node ≥ 20, zero npm
packages) next to Docker and Traefik, and exposes a **fixed, allowlisted** set of operations to
the CloudHost247 control plane over HMAC-signed HTTP.

```
CloudHost247 API  →  Deployment Queue (PostgreSQL)  →  Deployment Worker
                                                            │ signed HTTP (HMAC-SHA256)
                                                            ▼
                                                   Server Agent (this repo)
                                                            │ docker compose CLI
                                                            ▼
                                             /opt/cloudhost247/apps/<project>/
```

## Why an agent at all (spec §31)

- **The Docker socket never leaves the server.** The control plane cannot reach
  `/var/run/docker.sock` — there is no TCP Docker API, no `DOCKER_HOST`, no socket proxy.
- **Fixed operations only.** The agent executes exactly the operations in `src/server.js`'s route
  table: deploy, teardown, start/stop/restart, status, logs, healthcheck, backup, restore,
  metrics. There is no exec endpoint, no arbitrary path reads, no generic command surface.
- **Per-server secrets.** Each server's agent secret is independent, stored encrypted in the
  control plane (`server_credentials`), rotatable from the admin UI, and revoking it stops that
  agent cold without affecting any other server.

## Request authentication

Every inbound request must carry:

```
X-CH247-Agent-Id:   <agent id>
X-CH247-Timestamp:  <unix seconds, ±60s skew>
X-CH247-Nonce:      <random per request>
X-CH247-Signature:  hex(HMAC-SHA256(secret, agentId\n timestamp\n nonce\n METHOD\n path\n sha256(body)))
```

- Timestamp outside the window → rejected. Nonce seen before → rejected (replay protection).
- Signature mismatch → rejected, and the agent logs it.
- The mirror implementation lives in `cloudhost247-node/src/deployments/agent-protocol.ts`.
  The two files define **one protocol** and must be changed together.

## Install

```bash
sudo CH247_AGENT_ID=agent-xxxxx \
     CH247_AGENT_SECRET=<shown once by the admin portal> \
     CH247_CONTROL_URL=https://portal.cloudhost247.com \
     ./install.sh
```

The installer creates a dedicated `cloudhost-agent` system user, installs a hardened systemd
unit, and writes the environment file root-only (`/etc/cloudhost247-agent.env`, 0600).

### Manual run (testing)

```bash
CH247_AGENT_ID=test CH247_AGENT_SECRET=... CH247_CONTROL_URL=http://localhost:3000 \
CH247_BIND=127.0.0.1 CH247_PORT=8787 node src/server.js
```

## Network posture

- Default bind `127.0.0.1:8787`. Put the agent behind Traefik with a TLS router restricted to
  the control plane's IPs, or use a firewall allowlist + WireGuard tunnel. Never expose it raw
  to the public Internet (the signature scheme is strong, but there is no reason to accept the
  traffic at all).
- Traefik itself runs in the `cloudhost247-traefik` external network; deployments generated by
  the platform attach only their `app` service to it (see
  `cloudhost247-node/src/deployments/compose-generator.ts`).

## Isolation model (spec §32)

Each deployment gets its own directory, compose project, network, named volumes, and `.env`
(0600). One customer's application is never in another customer's compose project:

```
/opt/cloudhost247/apps/c<customer>-<install>/
├── compose.yaml     # generated from the application manifest — regenerated on update
├── .env             # secrets for THIS deployment only, mode 0600
└── volumes/         # bind-mounted data + logical database dumps for backups
```

## Backups

`POST /v1/apps/:project/backup` produces a tar.gz of the project tree (including a
`pg_dumpall`/`mysqldump` when a database service is present) under
`/opt/cloudhost247/backups`, with a SHA-256 checksum the control plane records. Off-server
upload to S3/R2 happens in the control plane's backup job — this agent never sees object-storage
credentials, so a compromised agent cannot exfiltrate backups.

## Metrics

The agent reports CPU, memory, disk, load, uptime, and container counts every 60s to
`POST /api/v1/agent/report` (signed with the same secret). The control plane stores snapshots in
`server_metrics` and the admin/customer dashboards read from there.
